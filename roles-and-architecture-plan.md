# Ролі, workspace-модель та інтеграція бекенду — фінальний архітектурний план

## 1. Назва і статус документа

**Статус: PLANNING.** Це не імплементація — код тут не пишеться. Це
друга, повністю переглянута версія `roles-and-architecture-plan.md`:
перша версія (836 рядків) визначила правильний напрямок (три ролі,
Express+Prisma фундамент, поетапне вмикання) і майже все звідти
збережено, але кілька моделей даних у ній вели в глухий кут (обмін
"профіль належить АБО батькові, АБО класу", один `role` на юзера, один
довгоживучий JWT без відкликання). Ця версія виправляє саме ці місця,
не переписуючи те, що вже було правильним, і закриває розділи, яких
перша версія не торкалась узагалі (безпека сесій, offline-конфлікти,
idempotency, audit, observability, testing, deployment).

Документ самодостатній: щоб зрозуміти архітектуру, не потрібно читати
попередню версію.

## 2. Мета та межі

**Мета.** Дати один узгоджений, готовий до реалізації план для: (а)
рольової моделі дитина/батько/вчитель поверх уже існуючого
Express+Prisma+PostgreSQL бекенду; (б) безпечної, поетапної міграції
ігрового прогресу з `localStorage` на сервер; (в) наскрізних рішень
(стейт, роутинг, структура папок), які не доведеться переписувати,
коли з'являться реальні користувачі.

**Межі (що цей документ свідомо НЕ вирішує остаточно).**

- Не дає юридичного висновку щодо COPPA/GDPR-K — лише закладає технічні
  принципи мінімізації даних (розділ 32), остаточна перевірка —
  окремим юридичним кроком перед публічним запуском.
- Не обирає платіжного провайдера для майбутніх реальних покупок
  (розділ 31 launch-plan, `rekomendovana_model_monetyzatsii...`) —
  лише описує, де в моделі даних і API вони з'являться.
- Не прив'язує остаточно до Railway/Cloudflare Pages — ці варіанти
  лишаються практичною рекомендацією (як і в
  `backend-architecture-plan.md`), але код і конфігурація не повинні
  залежати від їхніх специфічних API.
- Не є фінальною специфікацією "Content Editor" (розділ 22
  launch-plan) — це майбутня, поза межами цього плану, залежна від
  ролі вчителя річ.

## 4. Поточний стан системи (перевірено проти коду)

Чесна відправна точка — усе нижче підтверджено читанням реального коду
репозиторію на момент написання, не з пам'яті:

| Шар | Стан |
|---|---|
| Frontend | React + Vite, без TypeScript. Навігація — `screen`-стан в `App.jsx`, умовний рендер (`{screen === "x" && <X/>}`), не роутер. |
| `App.jsx` | 559 рядків. Тримає `progress`, `screen`, `user`, десяток дрібніших `useState`. Містить доменну логіку-редьюсери (`recordFact`, `completeLevel`, `completeMaze`, `completeRace`, `purchaseAvatar` тощо) — забагато для контролера. |
| Lazy-завантаження | Більшість із 15 екранів (`src/screens/*.jsx`) — `React.lazy`; `MenuScreen` вантажиться одразу. |
| Прогрес | Повністю в `localStorage`. `src/game/progress.js` — єдина точка читання/запису/міграції: `STORAGE_KEY`, `BACKUP_KEY`, `CORRUPTED_KEY`, `CURRENT_SAVE_VERSION`, `migrateSave()`. |
| Backend | `server/` — живий, окремий Node-проєкт: Express + Prisma + PostgreSQL + JWT (`jsonwebtoken`), `bcrypt`, `zod`-валідація (`middleware/validate.js`), `express-rate-limit` (`middleware/authRateLimit.js`). |
| Схема БД | **Реально в Prisma лише одна модель — `User`** (`id`, `email`, `passwordHash`, `createdAt`, `updatedAt`, мапиться на таблицю `users`). Жодної іншої таблиці ще не існує в живій схемі. |
| API | Рівно три ендпоінти: `POST /api/auth/register`, `POST /api/auth/login`, `GET /api/auth/me` (+ `GET /api/health`). Жодного ендпоінта для профілів/прогресу/ролей. |
| Frontend-клієнт до бекенду | `src/game/apiClient.js` (обгортка над `fetch`), `src/game/auth.js` (`register`/`login`/`fetchMe`/`logout`, токен у `localStorage` під окремим ключем `kingdom-multiplication-auth-token`), `src/screens/AuthScreen.jsx` (повністю зверстаний UI для всіх станів). |
| `fetchMe()` | Написана в `auth.js`, **не викликається** з `App.jsx` (підтверджено: у файлі лише коментар, що це "окремий крок 4"). Сесія при старті застосунку не відновлюється. |
| Прапорець | `AUTH_ENABLED` у `src/config.js`, зараз `false` (з `VITE_AUTH_ENABLED`). Коли `false` — форма входу прихована, показується чесний стан "У розробці". |
| Синхронізація прогресу | **Не існує зовсім.** Жодних `profiles`/`game_saves`/`skill_statistics` таблиць, жодного ендпоінта, який приймає результат гри. |
| `ParentScreen.jsx` | **Уже реалізований** (не лише запланований) — одно-дитячий, читає локальний `progress` напряму, доступний без гейту з `MenuScreen`. |
| PWA/офлайн | Реалізовано (service worker, manifest, install-flow) — гра вже працює офлайн локально; це має зберегтися незалежно від бекенду. |
| Роутинг | `react-router` не встановлено. |
| Ролі | Не реалізовано: немає `role` на `users`, немає `classrooms`, немає жодного зв'язку користувач↔профіль. |
| Платні покупки | Не реалізовано (лише внутрішньоігрові монети за аватари). |

## 5. Глосарій доменних понять

Один термін — одна сутність. Уся решта документа використовує рівно ці
слова й не змішує їх:

| Термін | Означає | НЕ означає |
|---|---|---|
| **Дорослий акаунт** / `users` | Рядок БД з `email`+`passwordHash` — один дорослий, може мати одну або дві ролі. | Не дитина. Не профіль. |
| **Роль** / `role` | `PARENT` або `TEACHER` — приналежність дорослого акаунта до можливості; акаунт може мати ОБИДВІ (розділ 7). | Не те саме, що "робочий простір" (нижче). |
| **Робочий простір** / `activeWorkspace` | Який із своїх ролей дорослий зараз використовує в UI ("Моя сім'я" чи "Мої класи"). Похідне UI-поняття, не окреме поле авторизації на бекенді для кожного запиту — бекенд перевіряє належність ресурсу, а не "активний" workspace. | Не право доступу саме по собі. |
| **Дитина** | Жива людина, яка грає. Не є рядком `users`. | Не "дитячий акаунт" — акаунта в неї немає. |
| **Профіль** / `profiles` | Рядок БД, що представляє ігровий стан однієї дитини (герой, XP, монети, прогрес). Один профіль = один стабільний ігровий прогрес, незалежно від того, скільки дорослих чи класів з ним пов'язано. | Не "учень" як окрема сутність — те саме, що нижче. |
| **Учень** | Той самий рядок `profiles`, коли на нього дивляться через призму класу (`classroom_memberships`). Не окрема таблиця, не окремий обліковий запис. | Не новий тип сутності. |
| **Сесія пристрою (дитячого)** / `profile_devices` | Один виданий, окремо відкличний профільний токен для одного пристрою, на якому грає ця дитина. | Не те саме, що дорослий refresh-токен. |
| **Опікун** / `profile_guardians` | Зв'язок "цей дорослий бачить і керує цим профілем" (batко/мама/інший опікун). Багато-до-багатьох: у профілю може бути кілька опікунів, в опікуна — кілька профілів. | Не власність у сенсі "хто створив" — це саме право доступу й керування. |
| **Клас** / `classrooms` | Група профілів під керуванням одного або кількох учителів. | Не власник профілю — див. розділ 11. |
| **Членство в класі** / `classroom_memberships` | Зв'язок "цей профіль зараз бере участь у цьому класі". Може закінчитись (`LEFT`) без видалення профілю. | Не те саме, що бути "власністю" вчителя. |
| **Вчитель класу** / `classroom_teachers` | Зв'язок "цей дорослий викладає в цьому класі", з рівнем (`OWNER`/`TEACHER`/`ASSISTANT`). | Не guardian — учитель ніколи не отримує опікунські права над профілем. |
| **Спроба** / `game_attempts` | Один завершений раунд гри (рівень/тренування/міні-гра), надісланий з унікальним `attemptId`. | Не те саме, що "подія синхронізації" (нижче) — спроба є одним із типів події. |
| **Подія синхронізації** / sync queue event | Запис у локальній черзі, що чекає відправки на сервер (може бути спробою, зміною налаштувань, вибором аватара тощо). | — |
| **Приступність (доступ до перегляду прогресу)** | Похідне право: `guardian` АБО активний `classroom membership`+`classroom_teachers`. Не окрема таблиця дозволів у MVP. | Не те саме, що роль сама по собі — роль без зв'язку з конкретним профілем/класом нічого не відкриває. |

## 6. Архітектурні принципи

Наскрізні правила, яким підпорядковані всі рішення нижче:

1. **Гра спочатку працює локально.** Кожна нова серверна можливість —
   шар ПОВЕРХ локального режиму, не заміна. Дитина без акаунта, без
   інтернету, продовжує грати так само, як і зараз.
2. **Бекенд не блокує реліз.** Публічний запуск не чекає на жодну з
   рольових/серверних можливостей цього документа.
3. **Локальний прогрес не видаляється під час першої синхронізації.**
   Жоден крок міграції (розділ 24-25) не стирає `localStorage`, поки
   сервер не підтвердив успішне збереження — і навіть тоді локальна
   копія лишається робочим фолбеком.
4. **Міграція вводиться поступово, кожен етап оборотний.** Жоден
   feature flag (розділ 39) не є "точкою неповернення" — кожен можна
   вимкнути окремо від інших.
5. **Права перевіряються на сервері, завжди.** UI-гейти, приховані
   кнопки, `RequireRole` на роутері — це UX, не безпека (розділ 33).
   Кожен API-ендпоінт сам перевіряє належність ресурсу викликачу,
   незалежно від того, що показував фронтенд.
6. **Жодних сутностей-тупиків.** Модель даних із самого початку
   допускає: кілька опікунів на профіль, одночасну участь у класі й
   під опікою, дорослого з двома ролями одночасно (розділ 7-11) — щоб
   не переписувати схему, коли з'являться перші реальні сім'ї/класи,
   що не вписуються у спрощену модель.
7. **Не більше складності, ніж потрібно зараз.** React Context, не
   Redux (розділ 21). Express, не NestJS (уже прийняте рішення,
   зберігається). Cron + database-backed jobs, не Kafka (розділ 40).
8. **Сервер — джерело істини для всього, що можна підробити.** XP,
   монети, зірки, досягнення — рахує сервер над сирим результатом
   спроби, ніколи не приймає готове число від клієнта (розділ 27-28).

## 7. Ролі, workspaces і права

### 7.1 Чому "один `role` на юзера" — глухий кут

Перша версія цього документа пропонувала `users.role: "PARENT" |
"TEACHER"`. Проблема: реальний сценарій — одна доросла людина, що є і
батьком удома, і вчителькою в класі (вчителька молодших класів, чия
власна дитина теж грає) — не рідкість, а типова ситуація для шкільної
гри. Один enum змусив би або створювати другий акаунт на той самий
email (неможливо — `email` унікальний), або штучно забороняти цей
випадок.

**Нове рішення:**

```
user_roles
- user_id      FK -> users.id
- role         "PARENT" | "TEACHER"
- created_at
- UNIQUE(user_id, role)
```

Один `users` рядок може мати 0, 1 або 2 записи в `user_roles`. Для
MVP1 (розділ 41) типовий випадок — рівно один; модель просто не
забороняє другий, коли він знадобиться.

### 7.2 `roles` і `activeWorkspace`

Після входу сервер повертає повний список ролей користувача:

```json
{
  "user": { "id": "...", "email": "...", "displayName": "Олена" },
  "roles": ["PARENT", "TEACHER"]
}
```

`activeWorkspace` — **чисто фронтендове** поняття (не серверне поле
авторизації для кожного запиту): яку зі своїх ролей людина зараз
дивиться в UI. Зберігається в `AuthContext` (розділ 21), персистується
локально (`localStorage`, ключ окремий від профілю/прогресу), за
замовчуванням — остання використана, або перша з `roles`, якщо ще не
обирали.

```json
{ "roles": ["PARENT", "TEACHER"], "activeWorkspace": "PARENT" }
```

Якщо `roles.length > 1` — `MenuScreen`-заміна для дорослого
(`AdultHomeScreen`, розділ 20) показує перемикач "Моя сім'я" / "Мої
класи" у шапці. Якщо рівно одна роль — перемикач не показується
взагалі (нема чого перемикати).

**Важливо:** `activeWorkspace` НІКОЛИ не є єдиною перевіркою доступу
на бекенді. Запит "покажи дітей" перевіряється через
`requireRole("PARENT")` і `assertGuardianAccess` (розділ 17) незалежно
від того, який workspace зараз "активний" на клієнті — клієнт міг
збрехати чи мати застарілий стан.

### 7.3 Три ролі — визначення поведінки

**Дитина.** Грає. Не має `users`-рядка, не має email/пароля. Профіль
існує локально (гість) або прив'язаний до одного/кількох опікунів
і/або класу. Не бачить: налаштувань дорослого акаунта, батьківського/
вчительського дашбордів, реальних покупок, чужого прогресу.

**Батько/опікун (`PARENT`).** Має дорослий акаунт. Не грає сам (нічого
технічно не забороняє, але це не основний сценарій). Головні дії:
бачити прогрес пов'язаних профілів, керувати опікунськими зв'язками,
вирішувати реальні покупки (майбутнє). Пов'язаний з 0..N профілями
через `profile_guardians`.

**Вчитель (`TEACHER`).** Має дорослий акаунт. Головні дії: бачити
агреговану статистику класу й кожного учня, керувати `join_code`,
призначати тренування (розділ 30-31, окрема фаза). НЕ отримує
опікунських прав над жодним профілем свого класу — доступ лише через
активне членство (розділ 11).

### 7.4 Матриця прав доступу (за діями)

Розгорнута версія — з точним посиланням на те, ЯКИЙ зв'язок дає право
(не просто роль):

| Дія | Дитина (profile session) | Батько (guardian) | Вчитель (classroom membership) |
|---|---|---|---|
| Грати (бій/тренування/міні-ігри) | ✅ свій профіль | — | — |
| Бачити свій прогрес ("Мої знання") | ✅ | — | — |
| Бачити прогрес профілю | ❌ | ✅ лише де є `profile_guardians` запис | ✅ лише де профіль має АКТИВНЕ `classroom_memberships` у класі, де сам є `classroom_teachers` |
| Бачити прогрес чужого профілю/класу | ❌ | ❌ | ❌ |
| Редагувати email/пароль дорослого акаунта | ❌ (немає акаунта) | ✅ свій | ✅ свій |
| Купувати аватари за ігрові монети | ✅ | — | — |
| Реальна покупка (майбутнє) | ❌ (блокує parental gate) | ✅ | ❌ поза моделлю монетизації |
| Створити/приєднати дитячий профіль до себе | ❌ | ✅ (стає guardian) | ❌ (вчитель ніколи не guardian) |
| Створити клас, побачити/перегенерувати `join_code` | ❌ | — | ✅ лише свій клас, і лише `OWNER`/`TEACHER` (розділ 16) |
| Призначити тренування (майбутня фаза, розділ 31) | — | — (не входить у роль батька в MVP) | ✅ своєму класу |
| Редагувати рівні/контент (розділ 22 launch-plan) | ❌ | ❌ | 🔲 майбутнє, поза межами цього плану |
| Видалити/архівувати профіль | ❌ | ✅ якщо guardian, і пройдено parental gate (розділ 13) | ❌ (вчитель не може видалити чужий профіль — лише вивести з класу, розділ 9.4) |
| Вивести профіль із класу | ❌ (сам не може) | ✅ якщо guardian | ✅ якщо `OWNER`/`TEACHER` цього класу |

Принцип: **право визначається конкретним зв'язком
(`profile_guardians` / `classroom_memberships`+`classroom_teachers`),
не роллю саме по собі.** Роль відкриває КАТЕГОРІЮ дій (вчитель узагалі
може створювати класи), а конкретний ресурс — завжди через явний
зв'язок із цим ресурсом. Це навмисно НЕ RBAC із гранулярними
permission-рядками — для трьох ролей і моделі "зв'язок = право" це було
б надлишковим ускладненням; якщо колись знадобляться гранулярніші
дозволи (наприклад, "опікун-без-права-видаляти") — розширення
`profile_guardians.permission_level` (розділ 10), не нова система.

## 8. Модель дорослого акаунта

### 8.1 Що вже є

`users` (Prisma, реально в схемі): `id` (uuid), `email` (унікальний),
`passwordHash`, `createdAt`, `updatedAt`. Ендпоінти: `register`,
`login`, `me` — усі реалізовані й задеплоєні.

### 8.2 Що додається

```
users
- id                  (є)
- email               (є)
- passwordHash        (є)
- displayName         nullable  НОВЕ — "Пані Олена" замість email
│                                       у списку вчителів класу
- emailVerifiedAt      nullable  НОВЕ (розділ 12.4)
- createdAt / updatedAt (є)

user_roles            НОВА (розділ 7.1)
```

`displayName` — необов'язкове, не показується дитині ніде (лише
іншому дорослому: інший `classroom_teachers` того ж класу бачить ім'я
колеги, наприклад).

### 8.3 Реєстрація й вибір ролі (MVP1: лише реєстрація без ролі)

У MVP1 (розділ 41) реєстрація НЕ запитує роль одразу — акаунт просто
існує, `user_roles` порожній. Роль з'являється, коли людина вперше
виконує дію, що її потребує: "Додати дитину" → мовчки створює
`user_roles` запис `PARENT`; "Створити клас" → `user_roles` запис
`TEACHER`. Це свідома відмова від обов'язкового вибору ролі на формі
реєстрації (спрощує MVP1, не створює користувачів, які зареєструвались
і не знають, що обрати) — MVP2 (розділ 41) може додати явний вибір при
реєстрації, якщо це виявиться кращим UX, без зміни моделі даних.

### 8.4 Життєвий цикл дорослого акаунта

- **Реєстрація** — `email`+`password`, підтвердження email (розділ
  12.4) необов'язкове для MVP1 функціонально, але рекомендоване раніше
  (зменшує спам-акаунти); чіткий MVP-статус — розділ 41.
- **Логін** — email+пароль → access+refresh (розділ 12).
- **Зміна email/пароля** — вимагає повторного підтвердження паролем;
  відкликає всі активні сесії, крім поточної (розділ 12.3).
- **Password reset** — email-based, токен одноразовий,
  короткоживучий.
- **Видалення акаунта** — не видаляє автоматично профілі, де цей
  акаунт — guardian (розділ 9.4: окрема дія "передати опіку" або
  "видалити профіль" перед видаленням акаунта, або профіль лишається
  без жодного guardian, якщо був не єдиним — розділ 10.4).

### 8.5 Міграція наявних users (коли з'являється `user_roles`)

На момент впровадження стадії B (розділ 40) у `users` уже є реальні
зареєстровані акаунти (з MVP0, розділ 4) — жоден із них не має
`user_roles`-записів, бо цієї таблиці ще не існувало.

- **Сама Prisma-міграція, що додає таблицю `user_roles`, нічого не
  бекфілить.** Наявні users просто отримують нуль записів у новій
  таблиці — не потребує проходу по існуючих рядках `users` (на
  відміну від, наприклад, додавання NOT NULL-колонки — тут узагалі
  немає нової колонки на `users`, лише нова таблиця).
- **Наявні users НЕ отримують `PARENT` за замовчуванням.** Це прямий
  наслідок рішення розділу 8.3 (роль призначається дією, не
  реєстрацією) — застосовується однаково і до нових, і до вже
  існуючих акаунтів: перший, хто натисне "Додати дитину", отримує
  `PARENT`; ніхто не отримує роль без явної дії.
- **Явний вибір ролі при наступному вході — НЕ показується.** Раз
  роль призначається дією, а не окремим кроком (розділ 8.3), немає
  окремого "оберіть роль" екрана й для наявних users — вони просто
  бачать той самий `AdultHomeScreen`/`WorkspaceSelectionShell` з
  порожнім станом ("У вас поки немає дітей" / "У вас поки немає
  класів"), як і щойно зареєстрований.
- **Захист від випадкового перетворення на `TEACHER`:** оскільки роль
  видається ЛИШЕ явною дією "Створити клас" (окрема, явна кнопка, не
  побічний ефект жодної іншої дії), немає шляху отримати роль
  `TEACHER`, не бачачи прямо, що відбувається.
- **Rollback:** якщо стадію B потрібно відкотити — `ROLES_ENABLED=false`
  ховає весь новий UI; `user_roles`-таблиця й записи в ній лишаються в
  базі неушкодженими (Prisma-міграція, що додає таблицю, не
  скасовується автоматично при вимкненні прапорця — це окрема,
  свідома дія, якщо колись знадобиться повний технічний відкат, не
  типовий сценарій).
- **Feature flag захищає фронтенд до завершення бекенд-міграції:**
  `ROLES_ENABLED=false` — типовий стан під час розгортання
  Prisma-міграції на production, вмикається лише після підтвердження,
  що міграція застосована й нові ендпоінти відповідають (той самий
  принцип поетапного вмикання, розділ 39).

## 9. Модель дитячого профілю

### 9.1 Чому дитина не має власного акаунта

Свідоме, збережене з першої версії рішення, узгоджене з
`launch-plan.md` розділ 10 ("без реєстрації, без імені, без email" для
першого релізу):

- Реєстрація дитини email+паролем вимагала б перевіреної батьківської
  згоди на етапі реєстрації — юридичний тягар, якого зараз немає і
  який не потрібен, якщо дитина ніколи не створює обліковий запис.
- Діти орієнтовно 8-12 років реалістично не мають/не пам'ятають
  власний email і пароль — будь-яка форма входу з цими полями стає
  бар'єром, який фактично долає дорослий за дитину, роблячи "дитячий
  акаунт" фікцією.
- Менше персональних даних узагалі (розділ 32) — профіль не містить
  жодного контактного чи ідентифікаційного поля дитини.
- Простіший UX: "вибери, хто грає" (картки з аватарами) замість форми
  логіну.

Профіль — рядок БД без `email`/`passwordHash`, з нуля або кількома
зв'язками до дорослих (`profile_guardians`) і опційним зв'язком до
класу (`classroom_memberships`). "Вхід" дитини — вибір профілю на
довіреному пристрої й, за потреби, короткий PIN (розділ 13.1), не
автентифікація в класичному сенсі.

### 9.2 Модель даних профілю

```
profiles
- id                    uuid
- display_name          ім'я/нік, що бачать guardian і вчитель — НЕ email,
│                        може бути вигаданим
- hero_level, xp, coins, stars, streak, selected_avatar_id
                         (ігровий стан, як зараз рахує progress.js)
- timezone               nullable, IANA-рядок (розділ 32) — для streak/
│                        daily-quest дня; якщо null, використовується
│                        UTC+сервер-визначена евристика (розділ 32.3)
- status                 "ACTIVE" | "ARCHIVED" | "PENDING_DELETION" (зведена таблиця статусів нижче)
- server_revision         int, зростає з кожним підтвердженим mutation (розділ 26)
- created_at, updated_at
- deleted_at              nullable (soft delete, розділ 9.4)
```

**Прибрано з першої версії:** `owner_user_id` і `classroom_id` прямими
колонками на `profiles`. Причина й заміна — розділ 10-11 нижче.

### 9.3 Життя профілю до будь-якого зв'язку з дорослим

Профіль може існувати ЛОКАЛЬНО (лише в `localStorage`, без жодного
рядка на сервері) необмежено довго — це поточна поведінка гри й
лишається основним шляхом для гостя (розділ 25 "Локальний гість").
Серверний рядок `profiles` з'являється лише в момент, коли: (а) батько
явно "усиновлює" локальний прогрес (розділ 24.2), або (б) дитина
приєднується до класу (розділ 25.1), або (в), рідше, створюється
порожній анонімний серверний профіль (розділ 25.1, з обмеженнями).

### 9.4 Повний життєвий цикл профілю

Не один `DELETE child`, що залишає профіль-сироту — кожна дія
життєвого циклу окрема, з чіткою семантикою й окремим правом доступу.
Ендпоінти нижче — семантичний контракт (розділ 16.1 дає повний
API-огляд; тут — фокус на тому, ЩО кожна дія робить і ХТО може її
виконати):

| Дія | Ендпоінт | Хто може | Що відбувається з класовим членством | Що з прогресом/досягненнями |
|---|---|---|---|---|
| Створення локального профілю | — (немає серверного запиту, розділ 9.3) | будь-хто, без акаунта | n/a | існує лише локально |
| Створення профілю батьком (з нуля, без локального прогресу) | `POST /api/v1/parent/profiles` | PARENT | не зачіпає | новий, порожній |
| Імпорт локального прогресу | `POST /api/v1/parent/profiles/claim-local-progress` | PARENT | не зачіпає | переноситься повністю (розділ 24.2) |
| Додавання другого guardian | `POST /api/v1/profiles/:profileId/guardians` | існуючий guardian цього профілю | не зачіпає | не зачіпає |
| Відв'язування guardian | `DELETE /api/v1/profiles/:profileId/guardians/:userId` | інший поточний guardian (не сам себе останнім, розділ 10.3) | не зачіпає | не зачіпає |
| Приєднання до класу | `POST /api/v1/profiles/me/classroom-membership` (profile session) | сам профіль (дитина/за допомогою дорослого) | створює `classroom_memberships` ACTIVE | не зачіпає |
| Вихід із класу | `DELETE /api/v1/classrooms/:classroomId/memberships/:profileId` | guardian АБО `classroom_teachers` цього класу (розділ 11.2) | `status → LEFT` | не зачіпає, лишається як є |
| Зміна класу | вихід + нове приєднання (два окремі виклики, не один "переміщення"-ендпоінт — явність важливіша за зручність тут) | guardian + сам профіль/дитина для нового приєднання | старе `LEFT`, нове `ACTIVE` | не зачіпає |
| Зміна display name | `PATCH /api/v1/profiles/:profileId` | guardian | не зачіпає | не зачіпає |
| Відкликання пристрою | `DELETE /api/v1/profiles/:profileId/devices/:deviceId` | guardian, parental gate (розділ 13.2) | не зачіпає | не зачіпає — лише цей конкретний пристрій більше не може писати |
| Передача профілю іншому guardian (наприклад, розлучення батьків, новий основний опікун) | `POST /api/v1/profiles/:profileId/transfer` | поточний guardian, parental gate | не зачіпає | не зачіпає — по суті додає нового guardian і, за бажанням ініціатора, прибирає старого в тій самій операції |
| Архівація | `POST /api/v1/profiles/:profileId/archive` | guardian, parental gate | активні членства лишаються `ACTIVE` технічно, але архівний профіль не показується в звичайному дитячому потоці (гра для цього профілю призупинена) | не зачіпає, лише призупиняє доступ |
| Soft delete | `DELETE /api/v1/profiles/:profileId` | guardian, parental gate | усі `ACTIVE` членства переходять у `REMOVED` | `profiles.status → PENDING_DELETION`, `deleted_at` встановлюється, дані НЕ стираються фізично |
| Період відновлення | — (просто вікно часу) | guardian може скасувати | — | рекомендація: 30 днів між `PENDING_DELETION` і фізичним видаленням |
| Відновлення | `POST /api/v1/profiles/:profileId/restore` | guardian, лише в межах періоду відновлення | членства НЕ відновлюються автоматично (`REMOVED` лишається `REMOVED` — вихід із класу під час "видалення" не скасовується мовчки, це окрема свідома дія, якщо потрібно) | повністю відновлюється |
| Остаточне видалення | фонова job (розділ 40.4), не прямий API-виклик користувача | автоматично, після спливання періоду відновлення | вже `REMOVED` | фізичне видалення персональних полів (`display_name`), АЛЕ `game_attempts`/`coin_transactions` (ledger, аудиторський слід) лишаються анонімізованими, не видаляються повністю — той самий принцип, що вже застосований до фінансових систем узагалі (розділ 15 — `RESTRICT` на ці таблиці) |

**Ключове правило:** видалення guardian-зв'язку НЕ видаляє профіль (є
й інші guardians або жоден — профіль просто лишається без опікуна,
розділ 10.4); видалення профілю (soft delete) — це єдина дія, що
насправді зупиняє профіль, і вона завжди вимагає parental gate.

## 10. Guardian relationships

### 10.1 Чому "один власник на профіль" — глухий кут

Перша версія: `profiles.owner_user_id` (nullable, один). Реальні
сценарії, яких ця модель не витримує: двоє батьків/опікунів однієї
дитини, що обидва хочуть бачити прогрес зі своїх акаунтів; дитина, що
одночасно вдома під опікою і в класі вчителя (мама хоче бачити
прогрес, І дитина ходить у клас, де той самий прогрес рахується для
статистики класу) — перша версія явно забороняла це "щоб не
розв'язувати конфлікти прав", але заборона означала переписування
схеми в перший же тиждень реальних сімей.

### 10.2 Нова модель

```
profile_guardians
- profile_id           FK -> profiles.id
- user_id              FK -> users.id
- permission_level      "FULL" (MVP1: єдине значення) — зарезервовано
│                        під майбутнє "перегляд без права видалення",
│                        не використовується для розрізнення в MVP1/MVP2
- created_at
- UNIQUE(profile_id, user_id)
```

Багато-до-багатьох: один профіль — кілька guardians (мама + тато);
один `user` (з роллю `PARENT`) — кілька профілів (кілька дітей).
`assertGuardianAccess(user, profileId)` (розділ 17.3) — єдина функція,
яку викликає кожен `/api/v1/parent/*` ендпоінт, що торкається
конкретного профілю.

### 10.3 Хто може додавати/прибирати guardian

- Додати другого guardian може лише вже існуючий guardian цього
  профілю (`POST /api/v1/profiles/:profileId/guardians`, розділ 9.4) —
  вводить email іншого дорослого; якщо в того немає акаунта —
  запрошення (email-лінк реєстрації, прив'язка відбувається після
  реєстрації).
- Прибрати guardian (`DELETE
  /api/v1/profiles/:profileId/guardians/:userId`) — може будь-який
  ІНШИЙ поточний guardian того самого профілю (не сам себе видалити
  останнім, якщо він єдиний — розділ 19.6 описує, що робити з
  "профілем-сиротою").
- Учитель ніколи не може додати чи прибрати guardian — не має до цього
  доступу за жодних умов.

### 10.4 Прибирання guardian не видаляє класове членство

`profile_guardians` і `classroom_memberships` — повністю незалежні
таблиці. Видалення батьківського зв'язку не чіпає `classroom_id`
жодним чином (бо такого поля вже немає — є окрема таблиця, розділ 11)
і не видаляє прогрес.

### 11.1 Модель

│                         зберігається у відкритому вигляді)

### 11.2 Ключові правила

- **Учитель ніколи не стає власником/опікуном профілю.** Доступ —
  ЛИШЕ поки `classroom_memberships.status = "ACTIVE"` для профілю в
  класі, де сам учитель має `classroom_teachers` запис.
- **Вихід із класу не видаляє прогрес.** `classroom_memberships.status
  → "LEFT"` — профіль і весь його прогрес лишаються незмінними, лише
  вчитель більше не бачить цей профіль у роcтері.
- **Зміна класу не втрачає профіль.** Дитина може мати `LEFT`-членство
  в старому класі й нове `ACTIVE`-членство в новому — той самий
  `profile_id` в обох записах (одна дитина — один стабільний профіль,
  розділ 9.1).
- **Профіль може одночасно мати guardian(ів) і активне класове
  членство** — саме той сценарій, якого перша версія уникала. Немає
  конфлікту прав, бо права різні (guardian: повний перегляд+керування;
  вчитель: перегляд агрегатів лише поки членство активне) і
  перевіряються незалежно (розділ 17).

### 11.3 Кілька вчителів на клас (розділ 16 — детальніше)

`classroom_teachers` замінює одиночний `teacher_user_id` саме тому, що
клас може мати асистента чи другого вчителя. Для MVP2 (розділ 41),
якщо співвчителі не потрібні одразу, таблиця все одно існує з
одиночним `OWNER`-рядком — не блокує появу другого вчителя пізніше без
міграції схеми.

## 12. Сесії та токени

### 12.1 Чому один довгоживучий JWT (поточний MVP-стан) — тимчасове, не фінальне рішення

Зараз (`backend-mvp-plan.md`, підтверджено кодом): `signToken({ sub,
email })`, немає refresh-flow, токен зберігається в `localStorage`.
Прийнятно для MVP0 (лише реєстрація/логін, без чутливих дій), але не
підходить, коли з'являються батьківські/вчительські дії над дитячими
профілями:

- Токен у `localStorage` доступний будь-якому JS на сторінці (XSS) —
  довгоживучий токен без відкликання, вкрадений один раз, працює, поки
  не спливе (тижні).
- Немає способу відкликати ОКРЕМУ сесію (вийти з одного пристрою, не з
  усіх).
- Немає розрізнення "дорослий" vs "дитячий профіль" на рівні токена —
  дитина технічно могла б виконати запит, що вимагає дорослого токена,
  якби колись отримала його (малоймовірно зараз, стає ризиком, коли
  з'являються чутливі дії).

### 12.2 Нова модель — два типи сесій, кожен зі своїм життєвим циклом

**Дорослий (user) сеанс:**

- **Access token** — короткоживучий JWT (рекомендація: 15 хвилин),
  payload `{ sub: user.id, roles: [...], kind: "user_access" }`.
  Зберігається **в пам'яті React-застосунку** (`AuthContext`
  state, розділ 21), НЕ в `localStorage`/`sessionStorage` — зникає при
  закритті вкладки, оновлюється прозоро через refresh.
- **Refresh/session token** — довгоживучий (рекомендація: 30 днів,
  ковзне вікно), зберігається в `HttpOnly`, `Secure`, `SameSite=Strict`
  (або `Lax`, якщо потрібні кросдоменні редіректи — обирається під
  реальний hosting-домен) cookie. Недоступний JS.
- `POST /api/v1/auth/refresh` — cookie автоматично додається
  браузером, повертає новий access token; ротація refresh-токена при
  кожному використанні (виявляє повторне використання вкраденого
  токена — якщо старий refresh використали двічі, усі сесії цього
  користувача негайно відкликаються).
- `POST /api/v1/auth/logout` — відкликає поточний refresh (видаляє
  server-side запис сесії, чистить cookie).
- `GET /api/v1/me/sessions` / `DELETE /api/v1/me/sessions/:id` —
  список активних дорослих сесій, можливість відкликати окрему.
- Зміна пароля/email — відкликає всі сесії, крім поточної.

**Дитячий (profile) сеанс:**

```
profile_devices
- id
- profile_id            FK -> profiles.id
- token_hash             хеш виданого профільного токена (не сам токен —
│                        розділ 20 той самий принцип, що й join_code)
- device_name            nullable ("Планшет на кухні")
- created_at
- last_seen_at
- expires_at              довгоживучий, але СКІНЧЕННИЙ (рекомендація:
│                          180 днів, ковзне вікно при активному використанні)
- revoked_at              nullable
```

- Профільний токен — JWT `{ sub: profile.id, kind: "profile" }`, БЕЗ
  жодного поля дорослого (без `role`, без `email`) — сама відсутність
  цих полів і є гарантією, що профільний токен не можна видати за
  дорослий.
- Кожен пристрій, на якому вперше "заводиться" профіль (розділ 25),
  отримує ОКРЕМИЙ запис `profile_devices` і окремий токен — не один
  спільний токен на профіль.
- Опікун бачить список пристроїв профілю (`GET
  /api/v1/profiles/:profileId/devices`) і може відкликати окремий
  (`DELETE /api/v1/profiles/:profileId/devices/:deviceId`) — видалення
  пристрою НЕ видаляє сам профіль чи його прогрес, лише робить цей
  конкретний токен недійсним.

### 12.3 Middleware та розрізнення типів токена

- `requireUserSession` — перевіряє `kind === "user_access"`, підвантажує
  `req.user` з `roles`.
- `requireRole("PARENT" | "TEACHER")` — тонка обгортка над
  `requireUserSession`, додатково звіряє, що потрібна роль є в
  `req.user.roles`.
- `requireProfileSession` — перевіряє `kind === "profile"`, звіряє
  `profile_devices` запис не відкликаний і не прострочений, підвантажує
  `req.profile`.
- **User access token і profile token НІКОЛИ не взаємозамінні** —
  кожен middleware явно відхиляє токен неправильного `kind` з
  `401 INVALID_TOKEN_KIND`, навіть якщо підпис валідний (захист від
  сценарію "дитячий пристрій випадково отримав дорослий токен через
  спільний код" чи навпаки).

### 12.4 CSRF, XSS і чесні межі захисту

Cookie-based refresh зменшує ризик крадіжки токена через XSS (JS не
може прочитати `HttpOnly` cookie), **але це не абсолютний захист**:

- CSRF стає новим ризиком для будь-якого mutating-запиту, що покладається
  на cookie: захист — `SameSite=Strict/Lax` як перша лінія, плюс
  custom header (`X-Requested-With` або double-submit CSRF-токен,
  що фронтенд читає з відповіді логіну й надсилає окремим заголовком,
  не cookie) для запитів, де `SameSite` сам по собі недостатній
  (кросдоменний фронтенд/бекенд-хостинг).
- XSS і далі потребує власного захисту незалежно від cookie-рішення:
  Content-Security-Policy заголовки, уникнення `dangerouslySetInnerHTML`,
  санітизація будь-якого user-generated тексту (display name, назва
  класу — розділ 33.4), дисципліна залежностей (регулярний `npm audit`
  у CI, розділ 39).
- Email verification (`emailVerifiedAt`) і rate limiting на
  логін/реєстрацію/password-reset — уже частково є (`authRateLimit`),
  лишається й розширюється на нові чутливі ендпоінти (розділ 34).

## 13. Parental gate і profile PIN

Дві різні речі під різними назвами — перша версія документа не
розділяла їх явно, тут — окремо.

### 13.1 Profile PIN

- Необов'язковий короткий PIN на профілі (`device_pin_hash` на
  `profiles`, розділ 9.2 — залишено з першої версії, лише
  перейменовано контекстно) — використовується ЛИШЕ коли на пристрої
  кілька дитячих профілів (`ProfileSwitcherScreen`, розділ 20).
- **Не є автентифікацією.** Захищає від випадкового вибору чужого
  профілю (брат/сестра переплутали картку), не від навмисного обходу.
- Не дає доступу до покупок, до батьківського/вчительського дашборду
  — жодних чутливих дій.
- Rate limit / зростаюча затримка після кількох невдалих спроб (3
  спроби → коротка пауза) — проти випадкового перебору, не проти
  зловмисника (для якого PIN узагалі не бар'єр за дизайном).

### 13.2 Parental gate

- Окремий, суттєвіший бар'єр: повторний ввід дорослого пароля АБО
  підтвердження, що на пристрої є активна дорослого сесія
  (`user_access` токен ще дійсний) — тобто те, що дитина сама
  відтворити не може, бо не має дорослого пароля.
- Майбутнє (не MVP1/MVP2, розділ 44): WebAuthn/passkey як альтернатива
  паролю.
- Челендж навмисно НЕ дитячий (не "скільки буде 7×8" — дитина, що вже
  вивчила множення, легко пройде такий "захист").

**Коли потрібен parental gate:**

| Дія | Гейт |
|---|---|
| Реальна покупка (майбутнє) | ✅ |
| Видалення/архівація профілю | ✅ |
| Передача профілю іншому guardian | ✅ |
| Перегляд батьківського дашборду на СПІЛЬНОМУ пристрої, де активна дитяча сесія | ✅ |
| Керування пристроями профілю | ✅ |
| Зміна критичних privacy-налаштувань | ✅ |
| Купівля аватара за ігрові монети | ❌ (внутрішньоігрова валюта, не реальні гроші) |
| Перегляд власного прогресу дитиною | ❌ |

## 15. Database constraints та індекси

Не покладатись лише на Prisma-рівневу валідацію — критичні правила
живуть у самій базі:

**Foreign keys, усі з явною cascade-політикою** (не залишати
"типовий" Prisma-дефолт мовчки):

| Зв'язок | Політика |
|---|---|
| `profile_guardians.profile_id → profiles.id` | `CASCADE` (видалення профілю прибирає зв'язки опіки) |
| `profile_guardians.user_id → users.id` | `RESTRICT` (не можна видалити акаунт, поки він єдиний guardian — розділ 19.6 вимагає спершу передати опіку) |
| `profile_devices.profile_id → profiles.id` | `CASCADE` |
| `classroom_memberships.profile_id → profiles.id` | `CASCADE` |
| `classroom_memberships.classroom_id → classrooms.id` | `RESTRICT` (архівація класу — окрема дія, не каскадне видалення членств) |
| `classroom_teachers.classroom_id → classrooms.id` | `CASCADE` |
| `game_attempts.profile_id → profiles.id` | `RESTRICT` (історія спроб — аудиторський слід, не видаляється разом із профілем; soft-delete профілю зберігає attempts) |
| `coin_transactions.profile_id → profiles.id` | `RESTRICT` (той самий принцип — ledger незмінний) |

**Унікальні обмеження (перелічені в моделі вище, зведено тут для
повноти):** `user_roles(user_id, role)`, `profile_guardians(profile_id,
user_id)`, `classroom_teachers(classroom_id, user_id)`,
`classroom_memberships(classroom_id, profile_id)`,
`inventory(profile_id, item_type, item_id)`, `game_attempts(attempt_id)`,
`progress_migrations(migration_id)`, `coin_transactions(idempotency_key)`
де застосовно, `assignment_targets(assignment_id, profile_id)`.

**Check-обмеження, де практично підтримується діалектом:**

- `profiles.coins >= 0` — від'ємний баланс можливий ЛИШЕ через явну
  адміністративну операцію поза звичайним API (не досяжно через
  застосунок; якщо колись знадобиться "борг" — окреме рішення, не
  мовчазний виняток із цього правила).
- `classroom_memberships.status IN ('PENDING','ACTIVE','LEFT','REMOVED')`.
- `profile_devices`: не можна створити новий активний запис із
  `revoked_at IS NOT NULL` одночасно (перевірка на рівні сервісного
  шару, якщо СУБД-check незручний для цього конкретного правила).

**Заборонені на рівні сервісного шару (складно виразити чистим SQL
check, але обов'язково перевіряється в транзакції, розділ 24):**

- Не можна створити `classroom_memberships` у клас зі `status =
  'ARCHIVED'`.
- Не можна використати `profile_devices` запис зі `status =
  'REVOKED'` для видачі нового access — middleware перевіряє це на
  кожному запиті, не лише при видачі.
- Не можна повторно купити той самий `inventory`-запис — `UNIQUE`
  обмеження робить другий `INSERT` неможливим, сервіс ловить
  конфлікт і повертає "вже куплено", не списує монети вдруге.

**Індекси** (окрім автоматичних на PK/unique):

- `profile_guardians(user_id)` — швидкий "список моїх дітей".
- `classroom_memberships(profile_id)` і `(classroom_id, status)` —
  "у яких класах ця дитина" і "активний ростер класу".
- `classroom_teachers(user_id)` — "мої класи".
- `game_attempts(profile_id, received_at)` — для дашбордів і
  пагінації історії.
- `coin_transactions(profile_id, created_at)`.
- `profile_devices(profile_id)`.
- `classrooms(join_code_hash)` — унікальний, для швидкого пошуку при
  приєднанні.
- `audit_logs(resource_type, resource_id, created_at)` — для перегляду
  історії конкретного ресурсу.

### 16.3 Уніфікований контракт помилок

```json
{
  "error": {
    "code": "PROFILE_ACCESS_DENIED",
    "message": "You do not have access to this profile.",
    "requestId": "..."
  }
}
```

`code` — стабільний, машинозчитуваний, стрічка `SCREAMING_SNAKE_CASE`;
`message` — англійською (внутрішня діагностика), НЕ локалізується на
сервері — фронтенд перекладає `code` в людське повідомлення через
власні i18n-ключі (той самий принцип, що вже застосований для
`EMAIL_ALREADY_EXISTS`/`INVALID_CREDENTIALS` у поточному `auth.js`);
`requestId` — той самий ідентифікатор, що йде в логи (розділ 35).

## 17. Authorization matrix

### 17.1 За ресурсами, не лише за ролями

Розширює матрицю розділу 7.4 конкретними технічними умовами для
кожної операції:

| Операція | Session kind | Роль | Resource rule | Parental gate |
|---|---|---|---|---|
| Отримати свій прогрес | profile | — | `token.profileId === requested profile` | ні |
| Надіслати спробу | profile | — | `token.profileId === profile` | ні |
| Побачити список своїх дітей | user | PARENT | `profile_guardians.user_id = self` | ні |
| Побачити прогрес конкретної дитини | user | PARENT | `assertGuardianAccess` | ні |
| Побачити учня класу | user | TEACHER | `assertTeacherClassroomAccess` | ні |
| Видалити профіль | user | PARENT | `assertGuardianAccess` | **так** |
| Архівувати профіль | user | PARENT | `assertGuardianAccess` | так |
| Передати профіль іншому guardian | user | PARENT | `assertGuardianAccess`, і цільовий user існує | так |
| Відкликати пристрій профілю | user | PARENT | `assertGuardianAccess` | так |
| Регенерувати join code | user | TEACHER | `assertClassroomOwnerAccess` (лише `OWNER`) | ні |
| Створити клас | user | TEACHER | немає (створює новий ресурс) | ні |
| Приєднати профіль до класу | profile | — | `token.profileId === profile`, клас `ACTIVE` | ні (розділ 20 — інші захисти) |
| Змінити email/пароль | user | будь-яка доросла | `own user account` | так, повторний пароль |
| Призначити тренування (майбутнє) | user | TEACHER | `assertClassroomOwnerAccess` (OWNER/TEACHER, не ASSISTANT) | ні |

### 17.2 Причина розділених guard-функцій

**Не використовується** одна універсальна `assertOwnsProfile`, що
змішує guardian-доступ і teacher-доступ — це різні права з різними
джерелами істини (`profile_guardians` проти
`classroom_memberships`+`classroom_teachers`), і змішування в одній
функції означало б, що баг в одній гілці логіки випадково відкриває
доступ через іншу.

Натомість — окремі, вузькі сервіси:

```
assertGuardianAccess(user, profileId)
  -> перевіряє profile_guardians(profile_id, user.id) існує

assertTeacherClassroomAccess(user, profileId)
  -> знаходить активні classroom_memberships цього profileId
  -> перевіряє, що user має classroom_teachers запис у ХОЧА Б ОДНОМУ
     з цих класів

assertProfileSessionAccess(token, profileId)
  -> token.kind === "profile" && token.sub === profileId

assertClassroomOwnerAccess(user, classroomId, allowedRoles = ["OWNER"])
  -> classroom_teachers(classroom_id, user.id).membership_role IN allowedRoles
```

Кожен контролер явно викликає РІВНО ту функцію, яка відповідає
природі запиту — немає жодного "загального" шляху доступу, який можна
випадково розширити для одного випадку й ненавмисно для іншого.

## 18. Frontend application shells

### 18.1 Навіщо потрібні окремі shells

Зараз (розділ 4) увесь застосунок — одне дерево під `App.jsx` з
`screen`-станом. Коли з'являються ролі, перше рішення при запуску —
**яке кореневе дерево показати**, і це рішення не повинно змішуватись
із рештою навігації (яка дитяча картка меню активна тощо):

```
GuestChildAppShell        гість без жодного акаунта (поточна поведінка,
                           типова для MVP1 більшості користувачів)
ChildProfileAppShell      дитина з прив'язаним профілем (той самий UI,
                           що й гість, лише прогрес звідкись синхронізований)
WorkspaceSelectionShell   дорослий залогінений, і `roles.length > 1` АБО
                           `activeWorkspace` ще не визначено — короткий
                           екран вибору "Моя сім'я" / "Мої класи"
ParentAppShell             дорослий, activeWorkspace = PARENT
TeacherAppShell            дорослий, activeWorkspace = TEACHER
```

### 18.2 Правило вибору shell

- Немає дорослої сесії, немає активної дитячої profile-сесії з
  batьківським/класовим зв'язком → `GuestChildAppShell` (= сьогоднішня
  поведінка гри, без жодних змін).
- Є активна дитяча profile-сесія → `ChildProfileAppShell` (той самий
  UI-потік, що й guest — різниця лише в тому, що прогрес синхронізується).
- Є доросла сесія на цьому пристрої, і на ньому НЕМАЄ активної дитячої
  profile-сесії → `WorkspaceSelectionShell` (якщо `roles.length > 1`)
  або одразу `ParentAppShell`/`TeacherAppShell` (якщо роль одна).
- **Спільний пристрій (сімейний планшет):** обидві сесії можуть
  співіснувати — дитяча profile-сесія в `localStorage` під своїм
  ключем, доросла user-сесія в пам'яті/cookie (розділ 12) під своїм.
  Застосунок за замовчуванням показує ту, яка активна "зараз" (типово
  — дитячу, бо це основний сценарій використання пристрою), з явною
  кнопкою "Я дорослий" на `MenuScreen`/`AdultHomeScreen`, що вимагає
  parental gate (розділ 13.2) для переходу в дорослий shell, і явною
  кнопкою "Повернутись до дитячого режиму" всередині дорослого shell —
  перемикання завжди явне, ніколи не мовчазне.

### 18.3 Гарантія проти змішування

Батько/вчитель на СВОЄМУ дорослому пристрої (не спільному сімейному)
ніколи не потрапляють у дитяче меню автоматично — вхід одразу веде у
`WorkspaceSelectionShell`/`ParentAppShell`/`TeacherAppShell`. Це прямо
відповідає вимозі: дорослий бачить дитячий інтерфейс лише свідомо
(через явний "переглянути як дитина" сценарій, якщо такий колись
знадобиться — не в MVP1/MVP2).

### 19.3 UX-стани, accessibility та повідомлення про помилки

Для нових дорослих і дитячих екранів (і для наявних, де з'являється
серверна залежність) потрібно явно передбачити: `loading`, `empty`,
`error`, `offline`, `stale` (кешовані дані, що показуються, поки йде
оновлення), `syncing`, `conflict`, `access denied`, `session expired`,
`revoked device`, `expired join code`, `duplicate membership`,
`migration in progress`, `migration failed`, `migration succeeded`.

**Дитина ніколи не бачить технічних деталей** — жодного `409 Conflict`,
жодного коду помилки на екрані. М'які формулювання ("Щось пішло не
так, спробуй ще раз" замість технічного тексту), і лише там, де
взагалі доречно щось показувати дитині (більшість зі списку вище —
речі, які бачить ЛИШЕ дорослий на своєму дашборді, не дитина в грі).

**Дорослому — конкретна дія:** повторити, перевірити мережу, увійти
знову, звернутися в підтримку, відновити профіль — не голий код
помилки без наступного кроку.

**404/403** — дитячі версії м'які ("Такої сторінки нема — повертаємось
у гру"), дорослі — конкретні ("У вас немає доступу до цього профілю").

**Accessibility (стосується всіх нових екранів, продовжує вже
пройдений accessibility-аудит наявних екранів):** keyboard navigation;
focus management у модалках (фокус переходить у модалку при відкритті,
повертається на тригер при закритті — уже реалізований патерн для
наявних модалок, поширюється на нові); підтримка screen readers
(`aria-label`, `aria-labelledby`); достатня контрастність (той самий
стандарт, що вже застосований — WCAG 2.2 AA); `prefers-reduced-motion`;
touch targets мінімум 44×44px (для дорослих екранів — трохи менша
вимога, ніж дитячі 72px рядки, бо дорослий інтерфейс не орієнтований
на дитячу моторику); повна локалізація (усі нові UI-рядки — через
`t()`, ключі в усіх 8 мовах, той самий процес, що вже застосовувався
для кожного попереднього екрана).

## 20. Routing

Зберігає рекомендацію першої версії (`react-router`), уточнює
застереження, додає деталі, яких там не було.

### 20.1 Що замінюється

- `screen === "x"` умовний рендер → маршрути.
- Ручний `window.history.pushState`/`popstate` хак у `GameScreen.jsx`
  → навігаційний блокер (конкретне API залежить від версії
  `react-router`, наявної на момент імплементації — **перед
  впровадженням обов'язково звірити актуальну документацію
  встановленої версії**, а не покладатись на назву можливості з
  пам'яті; якщо потрібна можливість виявиться нестабільною чи
  відсутньою в обраній версії — використати ізольований власний
  navigation guard, той самий підхід, що вже працює зараз, не
  блокуючи впровадження решти роутингу через це).

### 20.2 Обов'язкові guard-компоненти

```
RequireUserSession    редірект на /auth, якщо немає дорослої сесії
RequireProfileSession редірект на /switch-profile, якщо немає дитячої
RequireRole role="PARENT"|"TEACHER"
RequireWorkspace workspace="PARENT"|"TEACHER"   (UX-зручність, не заміна
                                                  RequireRole — сервер усе
                                                  одно перевіряє кожен запит)
```

Кожен такий guard — **лише UX**: приховує/перенаправляє, не є заміною
серверної перевірки (розділ 6, принцип 5; розділ 33.1).

### 20.3 Інші обов'язкові деталі

- **404/403 екрани** — дитячі версії м'які, дорослі — конкретні (розділ 19.3).
- **Redirect після логіну/логауту** — на збережений "куди йшов" URL
  (логін) або на `/` (логаут).
- **Відновлення маршруту після refresh** — прямий URL (`/parent/child/42`)
  має працювати після F5, не лише через клік у застосунку — вимагає
  SPA fallback на хостингу (розділ 37).
- **Browser back** — природний з роутером; окремо перевірити сценарій
  виходу з активного бою (те саме місце, де раніше був хак) під час
  міграції — регресійний тест обов'язковий (розділ 38).
- **Вибір `createBrowserRouter` (потребує SPA-фолбек на хостингу) проти
  `HashRouter`** (`/#/parent/...`, працює на будь-якому статичному
  хостингу без конфігурації) — рішення відкладається до вибору
  конкретного хостинг-провайдера (розділ 37); документ не прив'язує
  архітектуру до жодного з двох варіантів заздалегідь.

### 20.4 Коли впроваджувати

Роутинг — **окремий, механічний крок** (крок 7 послідовності, розділ
40), не одночасний з винесенням редьюсерів (крок 2) чи з появою ролей
(крок 9+). Причина та сама, що й у першій версії: одночасна зміна
"як улаштований стан" і "як улаштована навігація" ускладнює regression-
тестування без реальної додаткової вигоди від паралельності.

Якщо пріоритет "менше залежностей" переважує на практиці — мінімально-
життєздатна альтернатива (без нової бібліотеки): формалізувати
`ALLOWED_SCREENS[role]` як явну мапу, перевіряти в одній обгортці
`navigateTo(screen)` навколо `setScreen`. Дає частину безпеки UX без
нової залежності, ціною втрати URL/back-button/code-splitting "з
коробки". Рекомендація лишається `react-router`, це — задокументований
свідомий компроміс, якщо обрано інакше.

## 21. State management

### 21.1 Що вже є і чому цього недостатньо

`useState(progress)` + десяток дрібніших у `App.jsx`, проп-дрилінг на
один рівень — працює, бо дерево неглибоке. Ролі додають дві нові
державні одиниці, потрібні у БАГАТЬОХ місцях дерева одночасно: "хто
залогінений, у якій ролі/workspace" і "який профіль зараз обраний"
(для дорослого з кількома дітьми/учнями) — і додають серверні дані, які
потрібно кешувати (список дітей, прогрес учня), що взагалі не
подібне до природи `progress` (локальний, синхронний, один власник).

### 21.2 Три чітко розділені шари, не один store

**1. `AuthContext`** (React Context, весь застосунок):

```
{ user, roles, activeWorkspace, sessionStatus,
  login, logout, refreshSession, switchWorkspace }
```

Обгортка над `auth.js`, замінює прямий `user`-`useState` в `App.jsx`
(та сама поведінка, інша труба — крок 3 послідовності, розділ 40).

**2. `GameProgressProvider`** — монтується ЛИШЕ в дитячому app shell
(`GuestChildAppShell`/`ChildProfileAppShell`):

```
{ progress, dispatch, persistLocal, syncStatus,
  pendingEventsCount, activeProfile }
```

Доменно чисті reducer-функції (розділ 22.3) виносяться з `App.jsx`,
викликаються через `dispatch`. **`progress` не йде в `AuthContext` і
не стає глобальним** — він потрібен лише всередині дитячого дерева, і
контекст, монтований лише там, не додає накладних витрат для
дорослого дерева, де його взагалі нема.

**3. TanStack Query (або еквівалент) — для серверного стану дорослих
екранів:**

```
список дітей, профіль дитини, батьківська статистика,
список класів, roster, деталі учня, assignments (пізніше),
список активних пристроїв, керування сесіями
```

**Явно НЕ через React Context як ручну заміну кешу** — Context не дає
безкоштовно ревалідацію, дедуплікацію запитів, фонове оновлення,
retry — усе те, заради чого існує серверний кеш-шар. `ActiveProfileContext`
(яка дитина зараз обрана в дашборді) лишається окремим, вузьким
контекстом (лише `{ activeChildId, setActiveChildId }`) — це UI-стан
вибору, не сам серверний прогрес.

### 21.3 Local UI state — не все глобальне

Лишається всередині конкретних екранів, без винятку: модалки, активна
вкладка, обрана дитина на конкретному dashboard-під-екрані (де це не
потрібно ділити з іншими екранами), purchase target, крок форми. Це
пряме продовження принципу з першої версії — не кожне значення
заслуговує на контекст чи кеш лише тому, що технічно можна.

### 21.4 Чому не Redux/MobX/Zustand

Масштаб застосунку (15 екранів, один "живий" видимий одночасно) не
виправдовує окрему бібліотеку — Context + TanStack Query вирішують усі
реальні проблеми (глибока передача значення, серверний кеш) без нової
концептуальної ваги. Якщо колись з'явиться справді складна
crossnavigational синхронізація (наприклад, real-time оновлення
дашборду вчителя, поки учень грає) — це привід для WebSocket-шару й
розширення TanStack Query, не для Redux.

## 22. Структура папок

### 22.1 Чому не launch-plan.md розділ 23 "як є"

Та пропозиція організована навколо ЗМІСТУ (`audio/`, `content/`,
`game/battle|memory|maze|race`, `progression/`, `persistence/`).
Реальна нова вісь складності — РОЛІ (хто це бачить), не механіка гри.
Робити обидві реорганізації одночасно — велика структурна зміна заради
малої негайної вигоди (поточні 20 файлів у `src/game/`, 15 у
`src/screens/`, 17 у `src/components/` — це не той обсяг, де пласка
структура вже реально заважає).

### 22.2 Цільова структура (додається поступово, не переносить наявне одразу)

```
src/
  screens/
    ...(наявні файли — без переміщення в MVP1)
    parent/                    НОВА підтека, MVP1/MVP2
      ParentDashboardScreen.jsx
      ChildProgressScreen.jsx     (переїжджає сюди; ЗАМІНЮЄ поточний
                                    ParentScreen.jsx на новій стадії —
                                    розділ 29, не одразу)
      ManageProfilesScreen.jsx
      ProfileDevicesScreen.jsx
      AccountSettingsScreen.jsx
    teacher/                    НОВА підтека, MVP2 — НЕ в parent/
      TeacherDashboardScreen.jsx
      ClassroomRosterScreen.jsx
      StudentDetailScreen.jsx
      TeacherAccountSettingsScreen.jsx
    ProfileSwitcherScreen.jsx   НОВИЙ, у корені screens/ (дитячий екран)
    JoinClassroomScreen.jsx    НОВИЙ, у корені screens/
  contexts/                    НОВА тека (розділ 21)
    AuthContext.jsx
    ActiveProfileContext.jsx
  app/                          НОВА тека, з'являється разом із роутингом
    router/
    shells/
      GuestChildAppShell.jsx
      ParentAppShell.jsx
      TeacherAppShell.jsx
      WorkspaceSelectionShell.jsx
  game/
    ...(наявні файли — без переміщення)
    reducers.js                 НОВИЙ (розділ 22.3, крок 2 — до ролей)
    roles.js                    НОВИЙ — ALLOWED_SCREENS[role]/клієнтські
                                 гейт-хелпери (лише UX, розділ 6/20.2)
    sync/                       НОВА підтека (розділ 24-25)
      claimLocalProgress.js
      syncQueue.js               (перевикористовує патерн черги з
                                   analytics.js)
```

### 22.3 Один виняток, який робиться незалежно від ролей

Винесення доменних редьюсерів (`recordFact`, `completeLevel`,
`completeMaze`, `completeRace`, `purchaseAvatar` тощо) з `App.jsx` у
`src/game/reducers.js` — чиста користь незалежно від ролей чи
роутингу, робить `App.jsx` готовим прийняти контекст/роутер, не
переписуючи одночасно кілька речей. Це крок 2 послідовності (розділ
40), виконується ПЕРШИМ, окремо.

### 22.4 Стратегія переносу — без "великого коміту перейменувань"

1. Нові модулі створюються одразу в новій структурі (`contexts/`,
   `app/`, `game/sync/`).
2. Наявні екрани/файли залишаються на місці, поки не змінюються
   функціонально.
3. Файл переноситься в новий шлях ЛИШЕ в тому самому коміті, де він
   реально змінюється по суті (наприклад, `ParentScreen.jsx` →
   `screens/parent/ChildProgressScreen.jsx` — саме в коміті, що додає
   серверні дані замість локальних, розділ 29, не раніше).
4. Ніколи не змішувати "перейменування/переміщення файлів" і
   "функціональна зміна" в одному diff, якщо цього можна уникнути —
   ускладнює code review й git blame без потреби.

## 23. Local persistence

### 23.1 Що вже є (без змін)

`src/game/progress.js` лишається єдиною точкою читання/запису
локального прогресу: `STORAGE_KEY`, `BACKUP_KEY` (попередній успішний
запис), `CORRUPTED_KEY` (нечитаний JSON для діагностики),
`CURRENT_SAVE_VERSION`, `migrateSave()`. Жодна серверна можливість не
замінює цей шар — усе, що нижче (розділ 24-25), **обгортає** його, не
видаляє.

### 23.2 Нові локальні ключі, що додаються (усі окремі від `STORAGE_KEY`)

| Ключ | Призначення | Розділ |
|---|---|---|
| `kingdom-multiplication-auth-token` | Дорослий access token (лише для MVP0-стану; після переходу на cookie-based refresh — розділ 12.2 — сам access token НЕ персистується тут, лишається в пам'яті; ключ прибирається на етапі впровадження нової сесійної моделі) | 12.2, 40 |
| `kingdom-multiplication-profile-token` | Профільний токен поточного пристрою (розділ 12.2) | 12.2 |
| `kingdom-multiplication-device-id` | Локальний `deviceId` (UUID), суто технічний ярлик (розділ 23.4) | 23.4, 25.6 |
| `kingdom-multiplication-sync-queue-v1` | Черга невідправлених подій синхронізації (розділ 25) — той самий патерн, що вже реалізований в `analytics.js` (`QUEUE_KEY`/`readQueue()`/`writeQueue()`), перевикористаний буквально | 25 |
| `kingdom-multiplication-active-workspace` | Останній обраний `activeWorkspace` дорослого на цьому пристрої (розділ 7.2) | 7.2 |

### 23.3 Правило "локальне завжди пишеться першим"

Кожна ігрова дія (завершення рівня, покупка тощо) записується в
`progress.js` СИНХРОННО й локально ПЕРШОЮ — так само, як і зараз.
Мережевий виклик (якщо є) — завжди ДРУГИЙ, фоновий, необов'язковий для
того, щоб UI показав результат дитині. Це саме те, що гарантує "гра
працює без інтернету" залишається буквально істинним, а не лише
гаслом (розділ 6, принцип 1).

### 23.4 Ідентичність пристрою (`deviceId`) — технічна підказка, не автентифікація

Локальний `deviceId` (UUID, згенерований і збережений один раз на
пристрої) використовується ЛИШЕ як технічна мітка: групування подій у
черзі синхронізації (`clientSequence` рахується в межах одного
`deviceId`, розділ 25.4), позначка "з якого пристрою" в списку
`profile_devices` для батька (розділ 12.2, `device_name` — людська
назва, `deviceId` — технічний UUID під капотом), діагностика.

**Явні обмеження:**

- `deviceId` НЕ є секретом і не замінює токен — сам по собі не дає
  жодного доступу до жодного API.
- Немає жодного fingerprinting (canvas/audio/шрифтовий тощо) —
  навмисна відмова від агресивної ідентифікації дітей навіть заради
  зручності (розділ 32.1, мінімізація даних).
- Очищення `localStorage` (вручну користувачем чи браузером) створює
  НОВИЙ `deviceId` — це очікувана, прийнятна поведінка (пристрій
  просто виглядає як "новий" для чергового `profile_devices` запису
  при наступному підключенні), не помилка, яку потрібно "лагодити"
  складнішою ідентифікацією.

## 24. Міграція localStorage

### 24.1 Що потрібно підтримати (повний перелік станів)

- Порожній `localStorage` (перший запуск).
- Старий `saveVersion` (уже підтримано `migrateSave()`).
- Пошкоджений JSON (уже підтримано — падає у `CORRUPTED_KEY`, гра
  стартує з чистого стану, не крашиться).
- Частково відсутні поля (уже частково підтримано міграціями
  версій).
- Локальний backup (`BACKUP_KEY`) — уже є.
- **Новий стан, якого зараз немає:** повторний імпорт того самого
  локального прогресу; імпорт у ВЖЕ існуючий серверний профіль (не
  лише "створити новий"); вибір між merge та create-new, якщо
  локальний і серверний прогрес одночасно існують і не збігаються.

### 24.2 Потік "усиновлення" (claim-local-progress) — UX і технічні кроки

1. Батько на дитячому пристрої (або сам на своєму, дивлячись у гру
   через дитячий пристрій) натискає "Синхронізувати цей пристрій".
2. Показ **preview**: скільки рівнів пройдено, скільки монет, які
   аватари — перш ніж щось відправляти (дитина/батько бачать, ЩО саме
   збережеться).
3. Показ **імені профілю-призначення**: якщо це перший імпорт —
   поле для імені дитини; якщо профіль батька вже існує (другий
   пристрій тієї самої дитини) — вибір "це той самий Іван" чи "це
   нова дитина".
4. **Підтвердження дорослого** — реєстрація/логін, якщо ще не
   залогінений, перед самим імпортом.
5. Можливість **скасувати** на кожному з попередніх кроків без
   жодних наслідків.
6. `POST /api/v1/parent/profiles/claim-local-progress` (розділ 16.1) —
   з унікальним `migrationId`, згенерованим на клієнті один раз при
   старті потоку (переживає повторні спроби відправки при збої
   мережі — розділ 26).
7. Локальний `progress` НЕ видаляється одразу.
8. Після успіху локальний кеш позначається прив'язаним до конкретного
   `profileId` (новий локальний прапорець, не сам `progress`) — це і
   є захист від наступного пункту.
9. **Захист від подвійного імпорту в двох дітей:** якщо локальний
   кеш уже позначений як прив'язаний до `profileId` А, повторна спроба
   "усиновити" його під профіль Б на тому самому пристрої заблокована
   на клієнті (попередження "цей прогрес уже прив'язано до Іванка")
   І на сервері (`migrationId` — той самий, `progress_migrations`
   унікальність повертає попередній результат, розділ 26).

### 24.3 Джерело істини — по стадіях

**Перша стадія міграції (одразу після `claim-local-progress`):**

- `game_saves.data_jsonb` зберігає ОРИГІНАЛЬНИЙ версійований снапшот —
  використовується для відновлення, аудиту міграції, fallback.
- Нормалізовані таблиці (`level_progress`, `skill_statistics`,
  `inventory`) заповнюються ПАРАЛЕЛЬНО, одним синхронним проходом при
  імпорті — не на льоту при кожному запиті.

**Після стабілізації серверної моделі (коли синхронізація вже
відпрацювала стабільно, розділ 39, стадія D):**

- Нормалізовані таблиці — операційне джерело істини для всього, що
  показує дашборд батька/вчителя і що рахує нагороди.
- `game_saves.data_jsonb` **більше не вважається паралельно
  рівноправним** джерелом істини — це історичний бекап і матеріал для
  reprocessing (розділ 40), не те, що читають "живі" запити.

**Правило розбіжностей:** якщо нормалізовані таблиці й останній
`game_saves`-снапшот колись розходяться (баг імпорту, ручне
втручання) — нормалізовані таблиці виграють для всього, що показується
користувачу; `game_saves` лишається доступним для ручного
розслідування й можливого reprocessing (розділ 27.3, розділ 40).

## 25. Offline sync

### 25.1 Три сценарії "заведення" серверного профілю — розведені явно

**Локальний гість.** Гра продовжує існувати повністю локально, без
жодного серверного `profiles`-рядка. Це типовий стан MVP1 для більшості
користувачів і лишається повноцінно підтримуваним назавжди, не лише
як перехідний стан.

**Порожній анонімний серверний профіль** (якщо колись знадобиться —
наприклад, для швидкого "спробувати на іншому пристрої" без готовності
логінитись одразу): якщо такий сценарій реалізується, ендпоінт що його
створює зобов'язаний мати: rate limit (за IP і за `deviceId`),
abuse-захист, мінімальну відповідь (жодних персональних полів),
обмеження розміру payload, і — головне — НЕ приймати довільні
"нагороди" від клієнта при створенні (жодного `initialCoins`/`initialXp`
з довільним значенням). **Це не входить у MVP1** (розділ 41) — основний
шлях "усиновлення" завжди авторизований дорослим (нижче).

**Прив'язка локального прогресу до батька** — основний, постійний
сценарій, `POST /api/v1/parent/profiles/claim-local-progress` (розділ
24.2), завжди вимагає активної дорослої сесії.

**Приєднання до класу** — `POST /api/v1/profiles/me/classroom-membership`
(profile session, розділ 16.1) — приєднує ВЖЕ активний профіль, не
створює новий і не дублює, якщо активний профіль на пристрої вже
існує (клієнт перевіряє наявність активного профільного токена перед
показом `JoinClassroomScreen`; сервер додатково не дозволяє
приєднання без валідної profile-сесії — join code сам по собі профіль
не створює).

### 25.2 Компроміс офлайн vs server-authoritative — прямо визнаний

Коли інтернету немає, сервер не може миттєво підтвердити нагороду.
Гра НЕ блокує дитину через відсутність мережі (принцип 1, розділ 6).
Натомість:

1. Гра завершується локально (як зараз).
2. Генерується унікальний `attemptId` (UUID, клієнт).
3. Результат одразу пишеться в локальний `progress` (як зараз, без
   змін до цього кроку).
4. Подія (спроба) потрапляє в чергу синхронізації.
5. UI показує **provisional reward** — той самий каскад нагород, що й
   зараз (розділ 19.1, `ResultsScreen` без змін), порахований
   локально за тими самими правилами, що діють зараз на клієнті.
6. Після відновлення інтернету подія відправляється.
7. Сервер обробляє її **idempotently** за `attemptId` (розділ 26).
8. Сервер повертає **confirmed reward** і нову `serverRevision`.
9. Клієнт звіряє локальний стан із підтвердженим.
10. За потреби — reconciliation (розділ 26.4).

### 25.3 Конфлікт двох офлайн-пристроїв — явно визначена поведінка

Сценарій: та сама дитина грає офлайн на двох пристроях (телефон і
планшет), обидва накопичують чергу, обидва згодом синхронізуються.

- **Завершені спроби** — жодного конфлікту за визначенням: кожна має
  унікальний `attemptId`, append-only, обидва пристрої просто додають
  свої події в один потік на сервері (розділ 26.3).
- **Агреговані числа** (mastery, XP, монети) — НІКОЛИ не приймаються
  як стан "звідки" клієнта; вони завжди перераховуються сервером над
  усіма підтвердженими подіями (розділ 26 матриця merge-політик) —
  тому "конфлікту" в звичному розумінні (чий стан правильний) не
  виникає, є лише порядок обробки подій.
- **Last-write-wins ДОПУСТИМИЙ лише для:** налаштувань (мова/звук —
  бажано взагалі per-device, не синхронізовані), обраного аватара
  (розділ 26 таблиця).
- **Last-write-wins НЕПРИЙНЯТНИЙ для:** монет (лише ledger),
  досягнень (union), завершених рівнів (max/переоцінка), streak
  (серверне обчислення за календарем, розділ 32).

### 25.4 Формалізація черги подій

Кожна подія в локальній черзі:

```
eventId            UUID, клієнт
profileId
deviceSessionId     ідентифікатор profile_devices запису
eventType           "attempt" | "avatar_selected" | "settings_changed" | ...
createdAt           клієнтський час
clientSequence       монотонний локальний лічильник (виявлення "не по порядку")
baseServerRevision   остання відома клієнту serverRevision (розділ 26.2)
saveVersion
payload
retryCount
lastAttemptAt
status               "pending" | "sending" | "confirmed" |
                      "failed_retryable" | "failed_permanent" | "conflict"
```

### 25.5 Поведінка відправки

- **Exponential backoff:** початкова затримка ~5с, подвоюється до
  стелі (рекомендація: 5 хвилин), скидається при успішній відправці
  будь-якої події.
- **Максимальний retry interval** — 5 хвилин (не рідше, щоб черга не
  "застрягала" на годинники при короткій мережевій нестабільності).
- **Retry після запуску застосунку** і **retry після `online` event
  браузера** — обидва тригери окремо, не лише таймер.
- **Batch-відправлення** — до N подій за раз (рекомендація: 20), не
  по одній, щоб не створювати шторм запитів після довгого офлайну.
- **Обмеження розміру черги** — стеля (рекомендація: 500 подій чи
  фіксований обсяг у байтах); при досягненні стелі — НЕ видаляти
  найстаріші непідтверджені події мовчки (вони можуть бути
  найважливішими, перша спроба після довгої перерви), радше показати
  користувачу м'яке попередження й призупинити локальний запис нових
  provisional-подій понад стелю, поки черга не розвантажиться.
- **`failed_permanent`** (наприклад, сервер відповів `400`
  validation error, не мережева помилка) — подія лишається в черзі
  для діагностики/підтримки, більше не ретраїться автоматично,
  позначається окремо в UI-статистиці синхронізації (не показується
  дитині як помилка — розділ 30).
- **Чому не можна видаляти pending-подію до підтвердження сервером:**
  це єдина гарантія, що результат гри не загубиться при збої мережі,
  закритті вкладки чи вимкненні пристрою до завершення відправки.

### 25.6 Чесні обмеження PWA/браузера

Формулювання "фонова синхронізація" НЕ означає, що браузер гарантовано
довідправить чергу після закриття застосунку. Background Sync API
підтримується не всюди й не гарантує виконання. Реальна модель: черга
надійно дожимається щоразу, коли застосунок ВІДКРИТИЙ і є мережа
(старт застосунку, `online`-подія, періодичний таймер, поки відкрито) —
не є гарантією "надіслано навіть якщо вкладку закрили назавжди". Це
прийнятний компроміс (провісні нагороди вже показані дитині локально),
але має бути описаний чесно, не як "фонова синхронізація працює завжди".

### 25.7 UI навколо статусу синхронізації

- Ненав'язливий індикатор (не для дитини як тривога) — маленька іконка/
  крапка в кутку меню: "все синхронізовано" / "N подій очікує" /
  "проблема з відправкою" (остання — лише якщо `failed_permanent`
  накопичились, і лише дорослому, якщо дорослий переглядає пристрій).
- Дитина ніколи не бачить технічних деталей (`409`, `attemptId`,
  "conflict") — м'які формулювання, якщо взагалі щось показується
  (розділ 37).

## 26. Conflict resolution

### 26.1 `serverRevision` на профілі

`profiles.server_revision` (int, розділ 9.2) зростає з КОЖНИМ
підтвердженим mutation. Кожен mutation-ендпоінт повертає нову
`serverRevision` у відповіді.

### 26.2 Що надсилає клієнт

Кожна подія синхронізації несе `baseServerRevision` (яку ревізію
клієнт востаннє бачив) і власний `eventId`/`attemptId`. Сервер:

- Приймає **комутативні** події (append-only спроби, ledger-операції)
  незалежно від `baseServerRevision` — порядок обробки не впливає на
  коректність підсумку.
- **Не дозволяє старому снапшоту перетерти новий прогрес** — повний
  `PUT /profiles/me/save` (не подієвий шлях, розділ 23) перевіряє
  `baseServerRevision`; якщо сервер уже просунувся далі (є новіші
  підтверджені події від іншого пристрою), повний снапшот-запис
  ВІДХИЛЯЄТЬСЯ з `409` + `CONFLICT`, а не приймається сліпо — клієнту
  повертається поточний серверний стан для локального reconciliation.
- Повертає **conflict-відповідь лише там, де автоматичне об'єднання
  справді неможливе** (по суті — лише для повного снапшот-шляху; для
  подієвого append-only шляху конфлікту в цьому сенсі не буває за
  дизайном — розділ 26.3 нижче).

### 26.3 Матриця merge-політик

| Дані | Політика |
|---|---|
| Завершені спроби (`game_attempts`) | append-only + idempotency за `attemptId` |
| Skill statistics (`skill_statistics`) | серверне агрегування над підтвердженими подіями, не приймається як готове число з клієнта |
| Level stars (`level_progress`) | max (найкращий результат виграє) або серверна переоцінка над подіями |
| Achievements | union (об'єднання розблокованого з усіх пристроїв) |
| Owned avatars (`inventory`) | union ПІСЛЯ серверної перевірки, що покупка справді відбулась (кожен запис має `source_transaction_id`) |
| Selected avatar | остання підтверджена user choice (за серверним `createdAt` події вибору, не за клієнтським — захист від розсинхронізованого годинника пристрою) |
| Coins | лише ledger (`coin_transactions`), НІКОЛИ last-write-wins поверх балансу |
| XP | серверна сума підтверджених нагород |
| Streak | серверне обчислення за календарними правилами профілю (розділ 32), не приймається з клієнта |
| Settings (гучність тощо) | last-write-wins допустимий |
| Мова/аудіо-налаштування | бажано локальні per-device (не синхронізуються взагалі — розділ 32.1) |

### 26.4 Події не по порядку

Сервер приймає події з `clientSequence`, що не є монотонним відносно
`received_at` (типово при синхронізації після довгого офлайну — кілька
подій різного віку приходять одним батчем). Обробка — за
`clientSequence` у межах одного `deviceSessionId` для порядку
обчислень, що від порядку залежать (наприклад, streak); для
незалежних подій (окремі `game_attempts`) порядок обробки не має
значення (кожна оброблюється сама по собі, ідемпотентно).

## 27. Server-authoritative rewards

### 27.1 Принцип

Фронтенд НІКОЛИ не надсилає готову нагороду. Заборонені як "істина" з
клієнта поля: `xpGain`, `coinGain`, `newBalance`, `ownedAvatars`,
`achievementUnlocked`. Клієнт надсилає СИРИЙ результат спроби:

```json
{
  "attemptId": "uuid",
  "mode": "battle",
  "contentId": "forest-01",
  "correctAnswers": 7,
  "mistakes": 1,
  "responseTimesMs": [2100, 3400, 1800],
  "startedAt": "...",
  "finishedAt": "...",
  "clientCreatedAt": "...",
  "contentVersion": "1",
  "rewardRuleVersion": "1",
  "questionGeneratorVersion": "1"
}
```

Сервер визначає: скільки монет, XP, зірок; чи відкрилось досягнення;
чи виконано щоденне завдання; чи можна отримати нагороду повторно.
Кожна серверна нагорода має: rule version, `attemptId`, запис в
історії транзакцій (`coin_transactions`), детермінований або
відтворюваний результат (той самий вхід + та сама `rewardRuleVersion`
= той самий вихід — важливо для reprocessing, розділ 40).

### 27.2 Офлайн ≠ виняток із правила

Для офлайн-подій локальний UI показує **provisional** нагороду,
пораховану локально за тими самими правилами, що зараз використовує
клієнт (тимчасово дублюючи серверну логіку локально, доки немає
мережі) — але це НЕ те, що зрештою записується як істина. Коли подія
синхронізується, сервер рахує заново над сирими даними й повертає
**confirmed** нагороду; якщо вона розходиться з provisional
(наприклад, зміна `rewardRuleVersion` між грою офлайн і синхронізацією)
— клієнт тихо коригує локальний стан до підтвердженого, без
драматичного UI (розділ 37 — "стан звірено", не "ваша нагорода була
неправильною").

### 27.3 Rule versioning і reprocessing

`content_version`/`reward_rule_version`/`question_generator_version`
зберігаються на кожному `game_attempts`-записі. Дозволяє: пояснити
різницю в нагородах між старими й новими грою; повторно обробити старі
events, якщо в правилах нагород знайдено баг (job над уже завершеними
`progress_migrations`/`game_attempts`, не над живим потоком); не
змішувати статистику з несумісних алгоритмів у mastery-порівняннях
(розділ 32.4).

## 28. Coins та inventory ledger

### 28.1 Ledger, не голе число

```
coin_transactions
- id, profile_id
- type ("LEVEL_REWARD"|"PRACTICE_REWARD"|"RACE_REWARD"|"PURCHASE"|
        "ADMIN_ADJUSTMENT"|"MIGRATION"|"REVERSAL")
- amount, balance_after nullable
- source_type, source_id, idempotency_key
- created_at
```

`profiles.coins` — кешоване похідне значення (для швидкого читання),
але джерело істини — сума `coin_transactions`. Кожна зміна балансу
створює запис у ledger, ніколи не змінює `profiles.coins` "мовчки".

### 28.2 Inventory

```
inventory
- profile_id, item_type, item_id
- acquired_at, source_transaction_id nullable
- UNIQUE(profile_id, item_type, item_id)
```

### 28.3 Купівля аватара — транзакційна й ідемпотентна

1. Перевірити баланс (над ledger-сумою, не кешованим числом, у межах
   транзакції).
2. Перевірити, що предмет ще не в `inventory` (UNIQUE-обмеження —
   другий `INSERT` фізично неможливий).
3. Списати монети (новий `coin_transactions` запис, `type: "PURCHASE"`).
4. Додати запис в `inventory` з `source_transaction_id`.
5. Commit — усе одним `DB transaction` (розділ 24).

Повторний запит на купівлю вже придбаного предмета: `idempotency_key`
(або сам факт наявності `inventory`-запису) — сервер повертає
попередній успішний результат, **не списує монети вдруге**.

## 29. Parent dashboard

### 29.1 Поточний стан → цільовий стан (не заміна, а еволюція)

`ParentScreen.jsx` **вже існує й працює** (розділ 4) — одно-дитячий,
локальний, негейтований. Еволюція, не переписування з нуля:

1. **MVP1, крок 1:** дані й далі локальні (як зараз), АЛЕ доступ
   гейтиться — посилання з `MenuScreen` прибирається для дитячого
   shell; на дорослому пристрої з'являється `ParentDashboardScreen`
   (новий "домашній" екран `ParentAppShell`, розділ 18), що для
   ОДНІЄЇ дитини показує рівно те, що сьогодні показує `ParentScreen`.
2. **MVP1, крок 2 (після синхронізації прогресу):** дані приходять з
   `GET /api/v1/profiles/:profileId/progress` (сервер), не з
   `localStorage` цього пристрою — батько дивиться зі свого телефону,
   дитина грає на планшеті. Файл переїжджає в
   `screens/parent/ChildProgressScreen.jsx` (розділ 22.4 — саме в
   цьому коміті, не раніше).
3. **MVP2:** якщо дітей кілька — над існуючим вмістом з'являється
   перемикач дитини (горизонтальні картки-аватари) — `activeChildId`
   у `ActiveProfileContext` (розділ 21.2), не глобально.

### 29.2 Розрахунковий шар — той самий, що вже є

`mastery.js` (`overallMastery`, `tableMastery`, `recommendTable`,
`weakestFacts`) лишається джерелом формул. Коли прогрес
синхронізується на сервер, ці самі формули переносяться (не
переосмислюються) у серверний сервіс, що рахує над `skill_statistics`
замість `progress.facts` — чиста функція, легко портується. Дублювання
логіки на бекенді уникається (розділ 33).

### 29.3 Гейтинг доступу

- Дитячий пристрій без активної дорослої сесії — `ParentDashboardScreen`
  узагалі не в маршрутах, до яких є доступ (розділ 20.2).
- Спільний пристрій (і дитячий, і дорослий стан одночасно) — перехід у
  дорослий shell вимагає parental gate (розділ 13.2, 18.2).
- "Скинути прогрес"/ручний експорт-імпорт **і далі НЕ додається** —
  свідоме, збережене рішення користувача: синхронізація через акаунт є
  заміною ручного бекапу.

## 31. Assignments

**[Пізніше]** — свідомо винесено з MVP1 і MVP2 (розділ 41). Кнопка
"Призначити тренування" в `TeacherDashboardScreen` (якщо взагалі
показується до цієї фази) має бути видима лише як "Скоро" —
**не активна кнопка без моделі позаду** (пряма вимога — активна кнопка
без бекенду ніколи не потрапляє в реліз).

### 31.1 Модель даних (готова наперед, щоб MVP2 не заблокувала пізнішу появу)

```
assignments
- id, classroom_id, created_by_user_id, type, title
- instructions nullable, target_config_json
- start_at nullable, due_at nullable
- status "DRAFT"|"ACTIVE"|"CLOSED"|"ARCHIVED", created_at

assignment_targets
- assignment_id, profile_id, UNIQUE(assignment_id, profile_id)

assignment_progress
- assignment_id, profile_id
- progress_value, required_value
- status, started_at nullable, completed_at nullable
```

### 31.2 Правила, коли фаза настане

- Призначення для всього класу (усі активні `assignment_targets`
  одразу) або для окремих учнів (обраний підмножина).
- Типи: "таблиця" (наприклад, таблиця на 7), "слабкі приклади",
  "перегони", "лабіринт", "кількість правильних відповідей".
- Учитель НЕ може змінювати основний прогрес дитини напряму (розділ
  30.3) — `assignment_progress` рахується ЛИШЕ з реальних
  `game_attempts`, що підпадають під `target_config_json` умову.
- Виконання assignment НЕ дублює XP/монети — сама спроба вже
  нагороджена звичайним шляхом (розділ 27); assignment — лише
  прогрес-трекер поверх тих самих подій, не паралельна економіка.
- Учень бачить призначені завдання у дитячому інтерфейсі
  (`AssignedTrainingScreen`, розділ 19.2) — м'яко, без тиску.
- Прострочення (`due_at` минув) НЕ карає дитину втратою прогресу —
  `status` переходить у `"CLOSED"`, накопичений `progress_value`
  лишається як є.

## 32. Privacy, data minimization, інтернаціоналізація та часова модель

Ці три теми об'єднані в один розділ, бо їх поєднує спільний принцип —
не збирати й не переносити більше даних/контексту, ніж реально
потрібно для функції.

### 32.1 Privacy та мінімізація даних

Технічні принципи (без юридичних гарантій — розділ 32.5):

- Мінімум персональних даних узагалі: дитячий профіль не має email
  (розділ 9.1); `display_name` може бути ніком, не справжнім ім'ям.
- Учитель не бачить email/контакти батьків (розділ 30.3).
- Батько не бачить чужих дітей (`assertGuardianAccess`, розділ 17.2).
- Учитель бачить лише учнів АКТИВНОГО членства свого класу (розділ
  30.3).
- Дані класу не індексуються публічно, немає публічних профілів
  дітей — жодного ендпоінта, що віддає дані профілю без авторизації.
- **Retention:** видалені (soft-deleted) профілі й акаунти
  зберігаються обмежений період (розділ 19.5 — "період відновлення"),
  після чого — фонова job остаточного видалення (розділ 40.4).
- **Account/profile deletion** — повний lifecycle у розділі 19.
- **Export даних дорослого акаунта** — [Пізніше] (розділ 44); модель
  даних не заважає його додати (усі дані вже структуровані по
  `user_id`/`profile_id`).
- **Audit trail** для критичних змін — розділ 35.
- **Аналітика для дітей мінімізована** — уже реалізований принцип
  (`src/game/analytics.js`): жодних імен, дат народження, точних
  адрес, контактів, вільного тексту в payload; лише анонімні технічні
  події. Цей принцип поширюється на всі майбутні серверні аналітичні
  потоки без винятку.
- **Raw answer history** (кожна окрема відповідь дитини на кожен
  приклад) віддається батькові/вчителю ЛИШЕ якщо для цього є реальна
  UX-потреба (наприклад, показати "останні 5 помилок у таблиці на 7")
  — за замовчуванням дашборди отримують лише агрегати (`summary`,
  розділ 30.2), не повний журнал відповідей.

### 32.2 Інтернаціоналізація

Гра вже має вибір мови (8 локалей, `react-i18next`, статичне
бандлування ресурсів). Ролі додають кілька нових розрізнень:

- **UI locale per device** — те, що вже є, залишається per-device
  (не синхронізується) — швидка зміна мови на конкретному пристрої не
  повинна "стрибати" на інших.
- **Child profile locale preference** — необов'язкове поле на
  `profiles` (не в MVP1-мінімумі, `[MVP2]`), якщо колись знадобиться
  "дитина завжди бачить гру українською незалежно від пристрою" —
  окреме від UI locale пристрою.
- **Adult account locale** — окреме поле на `users` (мова листів
  password-reset/email-verification), не змішується з дитячим.
- **Classroom content locale** — [Пізніше], якщо контент-редактор
  колись підтримуватиме мультимовний контент класу.
- **Серверні error codes НЕ локалізуються на сервері** (розділ 16.3) —
  завжди `SCREAMING_SNAKE_CASE`, локалізація — виключно на фронтенді.
- **`display_name`/назва класу НЕ перекладаються** — це власні назви,
  введені користувачем.
- **Timestamps зберігаються в UTC** на сервері завжди (розділ 32.3).

### 32.3 Часова модель

Для активності, streak і щоденних завдань:

- Сервер зберігає й порівнює час виключно в UTC.
- Кожен профіль має `timezone` (розділ 9.2, nullable IANA-рядок) АБО,
  якщо не встановлено, сервер визначає "день" евристично за часовим
  поясом останнього запиту (менш точно, але не блокує роботу без
  явного налаштування — прийнятний компроміс для MVP1).
- "День" для streak/щоденних завдань НЕ рахується просто за UTC для
  всіх профілів однаково — інакше дитина в UTC+3 бачила б зміну дня о
  3 ранку за своїм годинником.
- **Захист від маніпуляції годинником пристрою:** клієнтський
  `clientCreatedAt` приймається лише як довідкове поле; вирішальний
  для streak/щоденних завдань — серверний `received_at`, з розумним
  допуском на розбіжність годинників (рекомендація: ±5 хвилин
  приймається без питань, більше — подія все одно приймається для
  нарахування XP/монет, але НЕ впливає на streak-обчислення заднім
  числом).
- **Offline events можуть мати клієнтський timestamp**, але довіреним
  для будь-якого рішення про "новий день"/streak є лише серверний.
  Довга офлайн-сесія (кілька днів без мережі) не повинна дозволяти
  нескінченно "продовжувати" streak заднім числом — сервер рахує
  streak за фактичною послідовністю календарних днів, підтверджених
  подіями, не за тим, що стверджує клієнт про кількість зіграних днів.

### 32.4 Формули mastery — версіонування

`recommendTable`/`overallMastery`/`weakestFacts` (розділ 29.2)
отримують `masteryVersion`, аналогічно `rewardRuleVersion` (розділ
27.3) — зміна формули не ламає порівняння старих даних, версія
зберігається разом із агрегатом.

### 32.5 Юридична межа

Документ НЕ дає юридичних гарантій. Конкретні вимоги COPPA, GDPR-K і
локального законодавства щодо дитячих даних потребують окремої
юридичної перевірки перед публічним запуском із роллю "батько"/
"вчитель" (не потрібно для чисто локального MVP0-режиму, де сервер
взагалі не бачить дитячих даних).

## 33. Security

### 33.1 UI-гейти — це UX, не захист

Пряме, повторюване правило (розділ 6, принцип 5): `RequireRole`,
приховані кнопки, `ALLOWED_SCREENS[role]` — усе це покращує UX і
запобігає випадковим помилкам, але **жоден з них не вважається
захистом API**. Кожен ендпоінт сам перевіряє права незалежно від того,
що фронтенд показав чи приховав.

### 33.2 IDOR (Insecure Direct Object Reference)

Кожен ендпоінт, що приймає `:profileId`/`:classroomId`/`:userId` у
шляху, зобов'язаний пройти через відповідну `assert*Access`-функцію
(розділ 17.2) ДО будь-якого читання/запису даних цього ресурсу —
жодного "спочатку віддамо дані, авторизація — окремим middleware
пізніше в ланцюжку" без явної гарантії порядку виконання.

### 33.3 Токени

Розділ 12 повністю: короткоживучий access у пам'яті, refresh у
`HttpOnly`/`Secure`/`SameSite` cookie, окремий тип токена для
профільної сесії, явна відмова middleware приймати токен неправильного
`kind`.

### 33.4 XSS

- CSP-заголовки на бекенді.
- Жодного `dangerouslySetInnerHTML` без санітизації.
- User-generated текст (`display_name` профілю, назва класу,
  `device_name` пристрою) — санітизується при збереженні І при
  рендері (подвійний захист), рендериться як текст, не як HTML.
- Залежності — регулярний `npm audit`/еквівалент у CI (розділ 39).

### 33.5 CSRF

Розділ 12.4: `SameSite` як перша лінія, custom header/double-submit
токен для мутуючих запитів, де самого `SameSite` замало.

### 33.6 Join code brute force

Розділ 20 (нижче, деталізовано в розділі 34) — достатня ентропія,
rate limit, hashed storage.

### 33.7 Replay

`attemptId`/`migrationId`/`idempotencyKey` — ідемпотентність на
кожному чутливому мутуючому запиті (розділ 26.2-26.3) — повторне
надсилання того самого запиту не подвоює ефект.

### 33.8 Revoked session reuse

`profile_devices.revoked_at`/`user_sessions.revoked_at` перевіряються
на КОЖНОМУ запиті через відповідний middleware, не лише при видачі
токена — відкликаний токен перестає працювати негайно, не після
природного спливання.

### 33.9 Захист від role escalation

- `POST /api/v1/me/roles` додає роль лише СОБІ (`req.user.id`), ніколи
  чужому user.
- Жоден ендпоінт не приймає `role`/`membership_role`/`permission_level`
  напряму від клієнта для встановлення привілеїв іншому користувачу
  без окремої, явної, авторизованої дії (наприклад, `classroom_teachers.
  membership_role` змінює лише `OWNER` класу, розділ 16.2 патерн).

## 34. Validation і rate limiting

### 34.1 Загальні вимоги для кожного API

- Schema validation на вході (`zod`, уже використовується для
  `auth`-роутів — поширюється на всі нові роути без винятку).
- Максимальний розмір snapshot (`claim-local-progress` payload) —
  конкретна стеля в байтах (рекомендація: 512 KB — з запасом понад
  реалістичний розмір `progress.js`-снапшота).
- Максимальна кількість events у batch (`POST /profiles/me/attempts`)
  — рекомендація: 50 елементів за раз.
- XP/coins/stars — НІКОЛИ не приймаються напряму від клієнта (розділ
  27.1) — сервер приймає лише сирий результат спроби.
- `contentId`/`mode` — звіряються проти відомого переліку
  (level id existence, дозволені режими) — не довільний рядок.
- Timestamp sanity checks: `finishedAt >= startedAt`,
  `clientCreatedAt` не в майбутньому понад допустиму похибку годинника
  (розділ 32.3).
- Допустима кількість відповідей/response times — узгоджена з
  `contentId` (наприклад, рівень з 8 питаннями не приймає масив на 40
  response times без пояснення — flag для ручного review, не жорстка
  відмова, щоб не карати легітимні edge-cases).
- Rate limiting — уже є `authRateLimit` для `/auth/*`; поширюється на:
  `claim-local-progress` (5/год/user), `join-classroom` (10/год/IP+
  пристрій), `regenerate-code` (5/день/клас), `attempts` (генерозний,
  але обмежений — наприклад 300/год/профіль, з запасом понад реальний
  темп гри).
- Structured validation errors — той самий контракт помилок, розділ
  16.3, з деталями по конкретному полю у `metadata`, не лише загальний
  код.
- `requestId`/correlation ID — на кожному запиті (генерується на вході
  в middleware-ланцюжок, якщо клієнт не надав власний), проходить крізь
  усі логи цього запиту (розділ 35).

### 34.2 Ніколи не покладатись на клієнтську валідацію

Кожна перевірка, що існує на фронтенді (форма реєстрації, довжина
PIN, формат join code) — дублюється на сервері незалежно. Клієнтська
валідація — лише UX (миттєвий фідбек), не єдина лінія захисту.

## 35. Audit і observability

### 35.1 Мінімальний observability-набір

- Централізований error handler (Express — уже є базовий підхід,
  поширюється на всі нові роути).
- Structured logs (JSON, не вільний текст) — `requestId`, `route`,
  `status`, `latencyMs`, `userId`/`profileId` (без секретів) на кожен
  запит.
- `GET /api/v1/health` (уже є) і `GET /api/v1/ready` (новий —
  перевіряє підключення до PostgreSQL, для healthcheck оркестратора,
  відрізняється від `/health`, яка може відповідати "процес живий" ще
  до готовності БД).
- Метрики sync queue: розмір черги на бекенді (кількість `PENDING`/
  `RECEIVED` подій), середній час confirm.
- Кількість `progress_migrations` зі статусом `FAILED`.
- Кількість idempotency-replays (той самий `attemptId`/`migrationId`
  надіслано повторно) — індикатор нестабільної мережі клієнтів або
  бага в клієнтській черзі.
- Кількість authorization denials (`403`) по ендпоінту — сплеск може
  вказувати або на баг фронтенду, або на спробу зловживання.
- Latency API по ендпоінту (p50/p95/p99).
- Rate-limit events (скільки запитів відхилено, по IP/користувачу).
- Audit log критичних дій (розділ 36).
- Error tracking (структуровані винятки з stack trace, requestId).
- Окреме логування background/retry jobs (розділ 40) — статус кожного
  запуску, кількість оброблених/провалених елементів.

### 35.2 Що НІКОЛИ не логувати

Паролі, access/refresh токени, profile session secrets (лише хеші),
повні snapshot'и без конкретної діагностичної необхідності (і навіть
тоді — з обмеженим retention), дитячі персональні дані (яких, за
дизайном розділу 32.1, майже немає, але правило явне на випадок нових
полів у майбутньому).

## 36. Backup і disaster recovery

- Автоматичні backups PostgreSQL (щоденні, з розумним retention —
  рекомендація: 7 щоденних + 4 тижневих) — конкретна конфігурація
  залежить від обраного хостингу БД (розділ 38), принцип не
  прив'язаний до провайдера.
- Періодична перевірка відновлюваності backup (не лише "backup
  існує", а реальний тестовий restore на staging).
- Захист production-бази: окремі креденшали від dev/staging, обмежений
  прямий доступ (лише через Prisma Studio для власника проєкту,
  розділ 7.4 — поза межами прикладного API).
- **Окремі dev/staging/production середовища** — окремі `DATABASE_URL`,
  окремі `JWT_SECRET`, ніколи спільна база між ними.
- Prisma migrations — усі зміни схеми через `prisma migrate`, ЖОДНОГО
  ручного редагування production-схеми напряму (той самий принцип,
  що вже задекларований у `backend-mvp-plan.md`).
- Rollback strategy: кожна Prisma-міграція, що додає NOT NULL колонку
  без дефолту на непорожню таблицю, — двофазна (спершу nullable +
  backfill job, потім окрема міграція, що робить NOT NULL) — уникає
  downtime і уможливлює відкат проміжного стану.
- Feature flags (розділ 39) — сама їхня наявність є частиною
  disaster-recovery стратегії: проблемну стадію можна вимкнути без
  деплою нового коду.
- Відновлення game snapshot: `game_saves.data_jsonb` (розділ 24.3) —
  якщо normalized-import мав баг, можливий REPROCESSING над
  незмінним оригінальним snapshot (job, розділ 40.4), не потрібно
  просити користувача пройти гру заново.

## 38. Testing strategy

Розширює наявні 49 unit-тестів (`tests/logic.test.mjs`), не замінює.

### 38.1 Unit tests

Reducers (`game/reducers.js`, розділ 22.3); mastery-обчислення (уже
є); reward-обчислення (нові серверні формули, розділ 27); merge-
політики (розділ 26.3 — кожен тип даних окремим тестом: append-only
спроби, ledger-баланс, union-достягнення); authorization helpers
(`assertGuardianAccess`, `assertTeacherClassroomAccess` тощо, розділ
17.2 — з позитивними й негативними випадками); join code validation
(розділ 20); sync queue state transitions (розділ 25.4 — усі
переходи статусів); idempotency-сервіси (`attemptId`/`migrationId`
дедуплікація).

### 38.2 Integration tests

Auth (register/login/refresh/logout); guardian access (позитивний і
негативний — чужий профіль); teacher access (той самий принцип);
`claim-local-progress` (успіх, дублікат `migrationId`, надто великий
payload); дубльований `attemptId` (не подвоює нагороду); покупка
аватара (транзакційність, повторний запит); приєднання до класу
(успіх, прострочений код, повторне приєднання вже активного профілю);
відкликаний пристрій (запит з відкликаним токеном → `401`); role
switching (`activeWorkspace` не впливає на серверну авторизацію —
явний тест, що підтверджує принцип розділу 7.2).

### 38.3 E2E

Локальний гість без акаунта (гра повністю грається офлайн); реєстрація
батька; батько створює дитину; міграція наявного локального прогресу;
дитина продовжує грати на тому самому пристрої після міграції; батько
дивиться прогрес з ІНШОГО пристрою; вчитель створює клас; дитина
приєднується до класу; вчитель бачить лише свій ростер; доступ другого
вчителя (спільний клас, розділ 16); перемикання профілів на спільному
планшеті; завершення гри офлайн + синхронізація після відновлення
мережі; повторний retry того самого attemptId; logout; спливання
токена; видалення й відновлення профілю (розділ 9.4).

### 38.4 Security tests

IDOR (запит чужого `profileId` через `assertGuardianAccess`-захищений
ендпоінт); role escalation (спроба призначити собі роль напряму через
payload, не через призначений ендпоінт); неправильний тип токена
(profile token на user-only ендпоінт і навпаки); brute force join code
(rate limit спрацьовує); replay (повторний attemptId не подвоює
нагороду); надто великий snapshot (`413`); зловмисний JSON
(malformed/nested payload не валить сервер); застаріла ревізія (старий
`baseServerRevision` на повний snapshot-запис → `409`, не тихе
перезаписування); XSS у `display_name`/назві класу (санітизація,
розділ 33.4); CSRF (мутуючий запит без валідного header/токена
відхиляється); повторне використання відкликаної сесії.

### 38.5 Migration tests

Старі `saveVersion`; частково пошкоджений `localStorage`; повторна
міграція того самого `migrationId`; rollback (Prisma-міграція, що
скасовується без втрати даних); імпорт порожнього прогресу; імпорт
максимально реалістичного великого прогресу (усі 16 аватарів, усі 23
досягнення, повна історія `skill_statistics`).

## 39. Feature flags

Розбиває `AUTH_ENABLED` на під-прапорці (продовжує підхід першої
версії документа, уточнює семантику кожного — зокрема, замінює
розмиту назву `SERVER_AUTHORITATIVE` на конкретні під-прапорці):

| Прапорець | Залежить від | Кого стосується | Вимкнено = | Впливає на локального гостя? | Rollback | Можна лише для тестових? | Метрика перед наступним етапом |
|---|---|---|---|---|---|---|---|
| `AUTH_ENABLED` | — | усі, хто натискає "Акаунт" | форма прихована, "У розробці" (поточний стан) | ні | миттєвий (прапорець назад) | так | форма проходить ручний QA-чекліст |
| `ROLES_ENABLED` | `AUTH_ENABLED` | ті, хто реєструється | реєстрація без вибору дій-що-надають-роль | ні | так | так | перші N реєстрацій із роллю без помилок |
| `MULTI_ROLE_ENABLED` | `ROLES_ENABLED` | дорослі з двома ролями | `user_roles` другий запис не пропонується в UI (бекенд усе одно технічно дозволяє) | ні | так | так | немає плутанини в перемиканні workspace на тестових користувачах |
| `PARENT_PROFILES_ENABLED` | `ROLES_ENABLED` | батьки | "Додати дитину" недоступне | ні | так | так | створення профілю + `claim-local-progress` проходять без помилок |
| `CLASSROOMS_ENABLED` | `ROLES_ENABLED` | вчителі | "Створити клас" недоступне | ні | так | так | клас + join + ростер проходять без помилок |
| `PROFILE_SYNC_ENABLED` | `PARENT_PROFILES_ENABLED` | профілі, що синхронізуються | кнопка "Синхронізувати" недоступна | ні (без явного натискання) | так, і навіть після натискання — локальний прогрес лишається (розділ 6, принцип 3) | так | 0 втрат локального прогресу на тестовій групі |
| `OFFLINE_EVENT_QUEUE_ENABLED` | `PROFILE_SYNC_ENABLED` | синхронізовані профілі | події не чергуються, лише повний снапшот-бекап | ні | так | так | черга дожимається коректно після відновлення мережі в 100% тестів |
| `SERVER_REWARDS_ENABLED` | `OFFLINE_EVENT_QUEUE_ENABLED` | синхронізовані профілі | нагороди й далі рахує клієнт (як зараз) | ні | так, окремо від `SERVER_INVENTORY_ENABLED`/`SERVER_ACHIEVEMENTS_ENABLED` | так | серверна й клієнтська нагорода збігаються на 99%+ тестових спроб |
| `SERVER_INVENTORY_ENABLED` | `SERVER_REWARDS_ENABLED` | синхронізовані профілі | покупки й далі локальні | ні | так | так | 0 випадків подвійного списання монет |
| `SERVER_ACHIEVEMENTS_ENABLED` | `SERVER_REWARDS_ENABLED` | синхронізовані профілі | досягнення й далі локальні | ні | так | так | union-merge коректний на тестах двох пристроїв |
| `ASSIGNMENTS_ENABLED` | `CLASSROOMS_ENABLED` | вчителі | кнопка "Призначити тренування" не показується взагалі (не "сіра", розділ 31) | ні | так | так | [Пізніше] — не для MVP1/MVP2 |
| `REAL_PURCHASES_ENABLED` | `PARENT_PROFILES_ENABLED` | батьки | реальні покупки недоступні | ні | так | так | юридична й store-перевірка пройдена (розділ 44) |

`SERVER_AUTHORITATIVE=true` як єдиний прапорець НЕ використовується —
розбито на `SERVER_REWARDS_ENABLED`/`SERVER_INVENTORY_ENABLED`/
`SERVER_ACHIEVEMENTS_ENABLED` саме тому, що "усе на сервері" й
"монети на сервері, а досягнення ще ні" — різні, окремо тестовані
рівні довіри, і розмита назва одного прапорця приховувала б, яка саме
частина вже authoritative.

9. **Стадія — класи (MVP2).** `classrooms`, `classroom_teachers`,
   `classroom_memberships` (розділ 14), `TeacherDashboardScreen` та
   інші вчительські екрани (розділ 19.2, 30), `join_code`-захист

   *Flag:* `CLASSROOMS_ENABLED`.

    того, як класи стабільно пропрацювали.
11. **Реальні покупки** [Пізніше] — `REAL_PURCHASES_ENABLED`, лише
    після юридичної й store-перевірки (розділ 44).

## 42. Ризики та компроміси

Свідомо не приховані:

| Ризик | Чому приймається | Пом'якшення |
|---|---|---|
| Server-authoritative rewards (стадія D) — найризикованіший крок, переносить довіру з клієнта на сервер | Без нього неможливо гарантувати чесність економіки при кількох пристроях/класах | Останній крок rollout, окремі під-прапорці, тижні стабілізації синхронізації перед вмиканням (розділ 40) |
| Офлайн-provisional-нагороди можуть розійтися з підтвердженими | Гра не повинна блокувати дитину без мережі (принцип 1) | М'яке тихе звірення на клієнті (розділ 27.2), не драматичний UI |
| Background Sync у браузерах не гарантований | Технічне обмеження платформи, не рішення проєкту | Чесне формулювання (розділ 25.6), дожимання при кожному відкритті застосунку — не єдина покладена надія |
| Два вчителі одного класу — рідкісний, але можливий edge-case конфлікту дій (обидва одночасно регенерують код) | Малоймовірний, не варта повної CRDT-моделі складність | `OWNER`-обмеження на чутливі дії (розділ 16 приклад), останній запис виграє для решти |
| `timezone`-евристика без явного налаштування (розділ 32.3) неточна для мандрівних користувачів | Точне визначення вимагало б геолокації — зайва складність і privacy-ризик для дитячого продукту | Явне поле `timezone` доступне, якщо колись знадобиться точність; неточність впливає лише на межу дня для streak, не на сам прогрес |
| MVP1 без server-authoritative rewards означає, що синхронізований профіль теоретично можна підробити на клієнті до стадії D | Прийнятно для раннього MVP з малою кількістю користувачів; це саме та причина, чому стадія D взагалі існує окремим кроком | Rollout явно рухається до стадії D, не залишає її невизначено відкладеною |
| Юридична невизначеність COPPA/GDPR-K до окремої перевірки | Документ технічний, не юридичний | Розділ 32.5 — явне застереження, перевірка обов'язкова перед публічним запуском ролей |

## 43. Definition of Done

Для кожного етапу rollout (розділ 40) — конкретний, перевірний
критерій готовності перед переходом до наступного:

**Стадія A (`AUTH_ENABLED` + нова сесійна модель):** реєстрація/логін/
refresh/logout проходять повний цикл без ручного втручання; сесія
відновлюється після перезавантаження сторінки; відкликання однієї
сесії не зачіпає інші; жоден токен не логується (розділ 35.2).

**Стадія B (ролі):** guardian/teacher-доступ пройшли IDOR-тести
(розділ 38.4); наявні users отримали коректну поведінку міграції
(розділ 44); `RequireRole`-гейти не пропускають дитину на дорослі
екрани навіть прямим URL.

**Стадія C (синхронізація):** duplicate `attemptId` не дублює
нагороду; offline attempt синхронізується після reconnect; локальний
прогрес НЕ губиться в жодному тестовому сценарії (розділ 38.3);
revoked device більше не може писати; конфлікт двох пристроїв не
зменшує coins/XP (лише додає, ledger/append-only, розділ 26); метрики
й логи sync queue працюють (розділ 35.1); є задокументований rollback
(вимкнути `PROFILE_SYNC_ENABLED` без втрати вже синхронізованих
даних).

**Стадія D (server-authoritative):** серверна й клієнтська нагорода
збігаються на реалістичній тестовій вибірці; є можливість швидко
відкотити (`SERVER_REWARDS_ENABLED=false`) без даунтайму; жодного
випадку подвійного списання монет за час стабілізаційного періоду.

**MVP2 (класи):** учитель бачить лише свій ростер (перевірено проти
другого тестового класу); вихід із класу зберігає прогрес; join code
має rate limit і закінчується терміном дії; регенерація коду
інвалідовує старий негайно.

## 44. Відкладені рішення

Свідомо поза межами MVP1/MVP2, з чіткою причиною для кожного:

- **Гранулярні permission-рівні опікуна** (наприклад,
  "перегляд-без-права-видаляти") — `profile_guardians.permission_level`
  зарезервований (розділ 10.2), не заповнюється, поки не з'явиться
  реальний запит на таку відмінність.
- **Співучителі поза `OWNER`** — таблиця готова (`classroom_teachers`,
  розділ 11.1), повний UI управління ролями всередині класу —
  пізніше.
- **Assignments** (розділ 31) — модель даних готова наперед, сама
  фіча — окрема фаза після стабілізації класів.
- **Реальні покупки й вибір платіжного провайдера** — модель даних не
  визначена цим документом (лише позначено місце в `coin_transactions.
  type`/аудит-подіях), вимагає окремого юридичного й store-аналізу
  (App Store/Google Play дитячі покупки мають власні жорсткі вимоги)
  перед будь-яким технічним рішенням.
- **Content Editor** для вчителя — поза межами цього документа,
  залежний від ролі вчителя, але самостійний план.
- **WebAuthn/passkeys** для parental gate (розділ 13.2) — покращення
  UX пізніше, пароль лишається основним механізмом на старті.
- **Real-time оновлення дашборду вчителя** (WebSocket, поки учень
  грає) — розділ 21.4, привід для окремого технічного рішення, не
  частина базової TanStack Query моделі.
- **Export персональних даних дорослого акаунта** (право на
  портативність даних) — модель дозволяє (усі дані структуровані по
  `user_id`), сам ендпоінт — пізніше.
- **Багато-до-багатьох "клас↔клас" чи "дитина в двох класах
  одночасно"** — поточна модель (`classroom_memberships`) уже технічно
  ДОЗВОЛЯЄ кілька активних членств одночасно (немає обмеження "лише
  один активний клас на профіль" — розділ 11.1 навмисно не додає
  такого унікального обмеження понад `(classroom_id, profile_id)`),
  але UI/UX для одночасного перебування у двох класах не спроєктований
  у цьому документі — якщо знадобиться, це UX-розширення, не зміна
  моделі даних.
- **Юридичний висновок COPPA/GDPR-K** — розділ 32.5, обов'язковий крок
  перед публічним запуском ролей, не вирішується цим документом.
