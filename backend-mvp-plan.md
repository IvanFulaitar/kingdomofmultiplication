# План: легкий бекенд з автентифікацією і PostgreSQL (найвищий пріоритет)

Це — вузький, дійовий план на "зараз": мінімальний, задеплоюваний бекенд
із реєстрацією/логіном (email + пароль) і PostgreSQL, щоб уже почати
збирати користувачів. Це НЕ заміна `backend-architecture-plan.md` (той
файл лишається довідковим планом повної ігрової серверної архітектури —
NestJS, profiles, game_saves, покупки, статистика прикладів тощо). Цей
документ — свідомо вужчий перший крок: лише `users` + автентифікація, на
легшому стеку, щоб отримати робочий деплой найшвидше, без переробки
пізніше.

## 1. Стек (мінімалістичний, обраний саме під "легкий бек")

| Частина | Вибір | Чому |
|---|---|---|
| Сервер | Node.js + **Express** | Значно менше боілерплейту й концепцій, ніж NestJS (модулі/guards/DI) — швидший шлях до робочого деплою. `backend-architecture-plan.md` і далі лишається орієнтиром, якщо пізніше захочеться перейти на NestJS-структуру. |
| База даних | **PostgreSQL** | Уже обраний варіант у `backend-architecture-plan.md` — узгоджені дані (юзери, пізніше профілі/покупки/прогрес), транзакції, надійність. |
| Доступ до БД | **Prisma** | Типобезпечні запити й міграції однією командою (`prisma migrate`), не набагато важча за сирий SQL, але значно менше ручної роботи й помилок. |
| Паролі | **bcrypt** | Перевірений стандарт для хешування паролів — не варто писати власну реалізацію. |
| Сесії | **JWT** (jsonwebtoken) | Без окремого сховища сесій на сервері — простіше піднімати й масштабувати; для MVP довгоживучий токен без refresh-flow. |
| Валідація вхідних даних | **zod** | Компактна перевірка email/пароля на вході, без важких фреймворків. |
| Хостинг API + БД | **Railway** | Уже обраний варіант у `backend-architecture-plan.md`: API і Postgres в одному проєкті, приватна мережа між ними, простий деплой із GitHub, безплатний старт/дешевий Hobby-план. |

Якщо захочеться ще легше — можна замінити Prisma на голий пакет `pg` (без
міграцій "з коробки", лише SQL-файли вручну). Це трохи менше залежностей,
але без типобезпеки й зручних міграцій. Рекомендація лишається Prisma.

## 2. Структура репозиторію

Тримати бекенд у тому самому репозиторії, в окремій теці — найпростіше
для одного розробника (один `git push`, один Railway-проєкт із root
directory `server/`):

```
kingdomofmultiplication/
├── src/                      існуючий фронтенд — без змін
├── server/                   НОВЕ
│   ├── src/
│   │   ├── index.js            запуск Express, підключення роутів
│   │   ├── db.js               Prisma client (єдиний інстанс)
│   │   ├── routes/
│   │   │   └── auth.js         /register /login /me
│   │   ├── middleware/
│   │   │   └── requireAuth.js  перевірка JWT з заголовка Authorization
│   │   └── utils/
│   │       └── password.js     hash()/verify() навколо bcrypt
│   ├── prisma/
│   │   └── schema.prisma
│   ├── package.json            окремий, свій node_modules
│   ├── .env.example
│   └── .gitignore              .env, node_modules
```

Окремий репозиторій (`kingdom-api`) — теж варіант, чистіший для окремого
CI/деплою, але зайва організаційна вага для старту. Рекомендація —
почати з теки в тому самому репо, винести пізніше, якщо знадобиться.

## 3. Схема бази даних (мінімум для старту)

Лише одна таблиця — не додавати нічого "про запас":

```prisma
model User {
  id           String   @id @default(uuid())
  email        String   @unique
  passwordHash String
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt

  @@map("users")
}
```

Коли дійде черга до ігрового прогресу — нові таблиці (`profiles`,
`game_saves`, `level_progress`, `skill_statistics`...) з
`backend-architecture-plan.md` посилатимуться на `users.id` через
`userId` — ця таблиця вже буде готовим фундаментом, переробляти нічого
не треба.

## 4. Ендпоінти (мінімум)

```
POST /api/auth/register   { email, password } -> { token, user }
POST /api/auth/login      { email, password } -> { token, user }
GET  /api/auth/me         (заголовок Authorization: Bearer <token>) -> { user }
GET  /api/health          -> { ok: true }   — для перевірки, що деплой живий
```

`user` у відповіді — лише `{ id, email, createdAt }`, ніколи не
`passwordHash`.

## 5. Безпека (не пропускати навіть у MVP)

- bcrypt, мінімум 10 rounds — паролі ніколи не зберігати відкритим текстом.
- JWT підписаний секретом з env-змінної (`JWT_SECRET`, довгий випадковий
  рядок, генерується один раз і зберігається лише в Railway env, не в
  коді/репозиторії).
- zod-валідація: коректний формат email, пароль мінімум 8 символів.
- `express-rate-limit` на `/register` і `/login` — захист від
  перебору паролів.
- CORS — дозволити лише домен фронтенду (Cloudflare Pages / інший),
  не `*`.
- `helmet` — базові безпечні HTTP-заголовки.
- Ніколи не логувати паролі й токени (навіть у консоль при дебазі).
- `.env` — у `.gitignore` з першого коміту; лише `.env.example` з
  порожніми значеннями йде в репозиторій.

## 6. Порядок виконання

1. Ініціалізувати `server/` (`npm init`, встановити express, dotenv,
   prisma, bcrypt, jsonwebtoken, zod, cors, helmet, express-rate-limit).
2. Локально підняти PostgreSQL для розробки (Docker
   `docker run -e POSTGRES_PASSWORD=... postgres:16` або локальний
   інстанс) і `.env` із `DATABASE_URL`.
3. Написати `prisma/schema.prisma` з моделлю `User`, прогнати
   `npx prisma migrate dev --name init`.
4. Реалізувати `POST /register` (перевірка унікальності email, хеш
   пароля, створення юзера, видача JWT).
5. Реалізувати `POST /login` (пошук за email, звірка пароля через
   bcrypt, видача JWT).
6. Реалізувати `requireAuth` middleware (перевірка й розшифрування JWT
   із заголовка) і `GET /me`.
7. Додати валідацію (zod), rate-limit, CORS, helmet, `GET /health`.
8. Локально протестувати всі ендпоінти (curl/Postman/Insomnia):
   реєстрація, повторна реєстрація тим самим email (має впасти з
   зрозумілою помилкою), логін із правильним/неправильним паролем,
   `/me` із валідним/невалідним/відсутнім токеном.
9. Задеплоїти на Railway (кроки нижче).
10. Перевірити задеплоєні ендпоінти наживо тим самим набором тестів.

## 7. Деплой на Railway — чекліст

Це єдиний крок плану, який Клод не може виконати сам (немає доступу до
твого Railway-акаунта) — виконується вручну в браузері. `railway.json`
у `server/` уже прописує builder/healthcheck/start command, тож більшість
налаштувань Railway підхопить сам.

### Перед початком

- [ ] Код у `server/` запушений у GitHub (Railway деплоїть із репозиторію,
      не з локальних файлів).
- [ ] Локально `npm run dev` + повний curl-чекліст із `server/README.md`
      уже пройдені без помилок (розділ 6, крок 8) — не деплоїти те, що
      ще не перевірено локально.
- [ ] Згенерований `JWT_SECRET` (довгий випадковий рядок) записаний
      окремо — знадобиться вставити в Railway.

### Створення проєкту

- [ ] Новий проєкт на [railway.app](https://railway.app).
- [ ] Додати плагін **PostgreSQL** (`+ New → Database → PostgreSQL`) —
      Railway сам створить БД і власну змінну `DATABASE_URL` для НЕЇ.
- [ ] Додати сервіс із GitHub-репозиторію (`+ New → GitHub Repo`),
      обрати цей репозиторій.
- [ ] У Settings нового сервісу — **Root Directory: `server`** (це
      монорепо, інакше Railway спробує збирати весь репозиторій,
      включно з фронтендом).

### Змінні середовища сервісу (Variables)

- [ ] `DATABASE_URL` — НЕ вписувати вручну; використати посилання на
      Postgres-сервіс того самого проєкту: `${{Postgres.DATABASE_URL}}`
      (назва залежить від того, як Railway назвав плагін БД — зазвичай
      `Postgres`). Це і простіше, і використовує приватну мережу
      всередині проєкту (швидше й безпечніше за публічний proxy-URL).
- [ ] `JWT_SECRET` — вставити згенерований рядок.
- [ ] `CORS_ORIGIN` — адреса фронтенду (якщо фронтенд ще не задеплоєний
      — можна тимчасово лишити порожнім/`http://localhost:5173`, і
      повернутись сюди, коли з'явиться публічний домен фронтенду).
- [ ] `PORT` — можна не чіпати, Railway підставляє сам, а сервер уже
      читає `process.env.PORT`.

### Білд і старт (перевірити, що підхопилось з `railway.json`)

- [ ] Builder: Nixpacks (автовизначення Node.js за `package.json`).
- [ ] Start command: `npm run start` (сам скрипт усередині вже виконує
      `prisma migrate deploy && node src/index.js`).
- [ ] Healthcheck path: `/api/health`.

### Під час першого деплою — дивитись у Deploy Logs

- [ ] `npm install` пройшов без помилок.
- [ ] `postinstall` (`prisma generate`) відпрацював.
- [ ] У логах старту видно застосування міграції (`prisma migrate
      deploy` — або "Applying migration `init`", або "No pending
      migrations", якщо вже застосована раніше).
- [ ] У логах з'явилось `API listening on http://localhost:<PORT>`.
- [ ] Статус деплою в Railway — Active/зелений (healthcheck на
      `/api/health` пройшов).

### Після деплою — жива перевірка (даси мені URL, і я прожену)

- [ ] `GET https://<project>.up.railway.app/api/health` →
      `{"ok":true,"db":"connected"}`.
- [ ] Той самий curl-чекліст із `server/README.md` (register, дубль
      email, некоректний email, короткий пароль, login правильний/
      неправильний пароль, `/me` валідний/відсутній/невалідний токен,
      rate-limit) — тепер проти живого URL замість `localhost:3000`.
- [ ] У вкладці Postgres → Data перевірити, що таблиця `users` існує і
      в ній з'явився тестовий запис після реєстрації.
- [ ] Переконатись, що `.env` НЕ потрапив у GitHub (уже в `.gitignore`
      — просто звірити на GitHub, що файлу немає в репозиторії).

### Типові проблеми

- Білд падає одразу → перевірити Root Directory (`server`, не корінь
  репозиторію).
- `prisma migrate deploy` падає → перевірити, що `DATABASE_URL`
  правильно посилається на Postgres-плагін (`${{Postgres.DATABASE_URL}}`),
  і що сам плагін БД запущений (не в стані помилки).
- Healthcheck не проходить, деплой "крутиться" → перевірити логи
  застосунку на помилку старту (найчастіше — відсутній/неправильний
  `JWT_SECRET`, бо `signToken`/`verifyToken` кинуть виняток без нього
  ще до першого запиту, хоча сам процес при цьому не впаде — впаде лише
  конкретний запит; якщо ж падає ввесь процес — дивитись повний
  стектрейс у Deploy Logs).
- Пізніше, коли підключиться фронтенд і CORS блокуватиме запити —
  повернутись і оновити `CORS_ORIGIN` на реальний домен фронтенду.

Публічний URL матиме вигляд `https://<project>.up.railway.app` —
власний домен (напр. `api.kingdom.frontstart.com.ua`) можна прив'язати
пізніше, як і описано в `backend-architecture-plan.md`.

## 8. Свідомі обмеження цього MVP (не робимо зараз)

- Немає скидання пароля й підтвердження email — додати пізніше через
  будь-який email-провайдер (Resend/SendGrid), коли з'явиться реальна
  потреба.
- Немає refresh-токенів — JWT просто довгоживучий (напр. 30 днів);
  додати короткоживучі access + refresh, коли навантаження/безпекові
  вимоги це виправдають.
- Немає ролей і адмін-панелі — не потрібно для збору перших
  користувачів.
- Немає прив'язки ігрового прогресу до акаунта — це наступний етап,
  уже описаний у `backend-architecture-plan.md` (`profiles`,
  `game_saves`, `level_progress` тощо, усі через `userId`).
- Фронтенд поки й далі працює на `localStorage` — підключення до цього
  API (реєстрація/логін екрани, надсилання токена) робиться окремим
  наступним кроком, коли бекенд уже стабільно задеплоєний.

## 9. Як це узгоджується з `backend-architecture-plan.md`

Той документ — довідковий план ПОВНОЇ серверної архітектури гри
(NestJS, 10 таблиць, транзакційні покупки, статистика прикладів). Цей
план — навмисно вузький Крок 0 перед ним: та сама база даних
(PostgreSQL) і той самий хостинг (Railway), але легший фреймворк
(Express замість NestJS) і рівно одна таблиця (`users`), щоб отримати
робочий задеплоєний бекенд якнайшвидше. Таблиця `users` звідси
напряму стає фундаментом для `profiles`/`game_saves`/інших таблиць із
повного плану — переробляти нічого не доведеться, лише додавати нові
таблиці й посилання на `users.id`. Перехід із Express на NestJS
(якщо колись знадобиться) теж не вимагає зміни моделі даних — лише
роути замінюються на контролери поступово.
